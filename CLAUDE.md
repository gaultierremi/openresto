# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

### Run everything (recommended for local dev)

```bash
npm run dev          # starts backend (dotnet watch) + frontend (expo) concurrently
npm run dev:native   # the same stack, addressed so a phone running Expo Go can reach it
npm test             # the root dev scripts' own tests (node --test, no jest at this level)
```

Both pass `--kill-others --kill-timeout` to `concurrently`, so one half dying takes the other
down instead of leaving the backend squatting on `:8080` where the next `dotnet watch` cannot
bind. `concurrently` kills through `tree-kill`, which is what reaches the
`dotnet watch` → `dotnet run` → `OpenRestoApi` grandchild that actually holds the port.

`dev:native` exists because `openresto-frontend/.env` points the app at `http://localhost:8080`,
and in Expo Go `localhost` is the **phone**, so the app resolves it to itself and reaches no API
at all. `scripts/dev-native.mjs` resolves this machine's LAN address and passes it as
`EXPO_PUBLIC_API_URL`, which Metro bakes into the bundle at build time; `@expo/env` skips any key
already in the system environment, so that wins over the `.env` file rather than racing it.
Docker and podman bridges are filtered out deliberately — bring the compose stack up and their
`172.x`/`10.88.x` addresses appear alongside the real one, and picking those fails exactly the way
`localhost` does. Override with `OPENRESTO_DEV_HOST` / `OPENRESTO_API_PORT` when the guess is
wrong; the script exits rather than falling back to an address the phone cannot route to.

Which address that is comes from `openresto-frontend/scripts/lib/expo-go.mjs`, shared with
`npm run native:go` rather than reimplemented — the two answer the same question, and answering
it twice is how the answers drift. It asks the routing table (a connected UDP socket fixes the
local end of a route without sending anything) and only falls back to filtering interface names.
`OPENRESTO_DEV_HOST` is that lib's `HOST_ENV`, so both commands take the same override; the
lib imports node builtins only, so the root `npm test` needs no frontend install.

Both halves are launched by handing `concurrently`'s own JS entry to `process.execPath`,
never the `node_modules/.bin` shim: npm writes the bare name there as a POSIX sh file that
Windows cannot execute, and the `.cmd` beside it needs `shell: true`, which would then have
to quote the space-bearing commands. Anything else in `scripts/` that spawns tooling has the
same choice to make — `scripts/dev-native.test.mjs` pins it, and the `root-scripts` CI job
runs those tests on Windows as well as Linux.

### Running E2E tests (Playwright) — read before running

The full-stack rate limiters are gated on `ASPNETCORE_ENVIRONMENT` (see `OpenRestoApi/Extensions/ServiceCollectionExtensions.cs`): **Development** (plain `docker compose up`) allows auth 10/min, public 120/min, global 300/min, which is fine for clicking around and far too tight for the suite; **Testing** (the `docker-compose.e2e.yml` override) raises all three to 10000/min. **Always start the stack with the e2e override:**

```bash
docker compose -f docker-compose.yml -f docker-compose.e2e.yml up -d --build
npm run test:e2e --prefix openresto-frontend
```

Running against Development produces cascading 429s: pages that hydrate from rate-limited fetches (booking form, /locations, /settings) fail to render in time, booking POSTs exhaust their retries, and customer lookup returns null (rendered as a false "No booking found"). It looks like selector bugs and is purely rate-limit exhaustion.

To verify the environment, **repeat both `-f` flags on the exec**:

```bash
docker compose -f docker-compose.yml -f docker-compose.e2e.yml exec backend printenv ASPNETCORE_ENVIRONMENT
```

The bare `docker compose exec backend printenv ASPNETCORE_ENVIRONMENT` is not trustworthy here. Under podman-compose (the `docker` CLI on a Fedora host is usually a podman shim) `exec` re-injects the service environment as parsed from the compose files passed to _that_ invocation, so omitting the override re-applies `ASPNETCORE_ENVIRONMENT=Development` from `docker-compose.yml` to the exec session and shadows the container's real value. It reports `Development` for a container genuinely running `Testing` — which reads as "the override silently failed" and sends you rebuilding a stack that was already correct. `docker inspect <container> --format '{{range .Config.Env}}{{println .}}{{end}}'` always shows the truth. Plain Docker Compose doesn't rewrite env on exec, so the bare form is only misleading on podman.

The config uses `workers: 1` and a `globalSetup` that logs in once to `e2e/.auth/admin.json`; specs still use `postWithRetry`/`getWithRetry` and `expectVisibleWithReload` for the rare in-Testing collision.

**Smoke vs. extensive split**: a handful of `test.describe` blocks covering
the golden paths (home browse, the full booking journey, booking
confirmation, customer lookup, admin login/logout, admin dashboard) are
tagged `{ tag: "@smoke" }`. `npm run test:e2e:smoke` (`--grep @smoke`) runs
just that subset; `npm run test:e2e:extensive` (`--grep-invert @smoke`) runs
everything else; `npm run test:e2e` still runs the full suite for local
debugging. In CI (`.github/workflows/ci.yml`), `e2e-smoke` runs on every PR
and push; `e2e-extensive` is gated to `push` on `main` only, so PRs get fast
feedback on the golden paths and the full-depth run happens once per merge.
When adding a new spec, tag its `describe` block `@smoke` only if it covers
a path a broken deploy can't ship without — most new coverage belongs in the
extensive set by default (i.e., untagged).

### Release (tag-triggered)

```bash
# 1. Add a ## [x.y.z] - YYYY-MM-DD section to CHANGELOG.md
# 2. Bump "version" in package.json (root), openresto-frontend/package.json, and
#    openresto-cli/package.json, and <Version> in OpenRestoApi/OpenRestoApi.csproj, to the
#    tag without the v prefix, then regenerate the three lockfiles:
npm install --package-lock-only && npm install --package-lock-only --prefix openresto-frontend && npm install --package-lock-only --prefix openresto-cli
# 3. Confirm everything agrees before tagging (CI runs this too):
./scripts/check-release-version.sh v1.0.0
git tag v1.0.0
git push origin v1.0.0
```

Never hand-edit the lockfiles; `--package-lock-only` is what keeps their top-level `version` in sync.

**Pick the number by semver, not by habit.** A release containing any new feature is a minor bump, even a small one. Patch is for fixes only.

`scripts/check-release-version.sh` is the guard against a half-finished bump: it asserts the three `package.json`s, the three `package-lock.json`s, and a CHANGELOG section all agree with the tag. The `verify-version` job in `release.yml` gates all four image builds on it, so a mismatch fails the release before anything reaches GHCR. v1.6.0 shipped with all four version fields still reading `1.5.0`, which is what this exists to prevent.

The frontend's Expo config takes its `version` from `openresto-frontend/package.json` (`app.config.ts` imports it), so there is nothing to bump there. `app.json` deliberately carries no `version` key: `app.config.ts` overrides everything it sets, so a value there is silently dead.

This triggers `.github/workflows/release.yml`, which builds `linux/amd64` + `linux/arm64` images for backend, frontend, nginx, and the CLI; pushes them to GHCR (`ghcr.io/karanshukla/openresto-{backend,frontend,nginx,cli}:<tag>`); and creates a GitHub Release with the per-version CHANGELOG section as notes and a pinned `docker-compose.yml` as a downloadable asset.

`docker-compose.release.yml` in the repo is the self-hoster install template. It references `${OPENRESTO_VERSION:-latest}` — the release workflow substitutes the actual tag before attaching it to the release. Self-hosters can also run any version directly:

```bash
OPENRESTO_VERSION=1.0.0 docker compose -f docker-compose.release.yml up -d
```

## Code comments

A comment is the last resort, not the first. Work down this ladder and only write prose when all four rungs fail:

1. **Abstraction and encapsulation.** Business logic explained by a comment in a controller belongs in a domain-named method in `Core/Application/Services` instead. Arithmetic spelled out in a comment (`// 44px target minus 30px of rendered height`) belongs in named constants that compute it. The same coercion explained in two places belongs in one named helper (`ContactFields.Normalize`, `OpeningHours.GetHoursForDay`).
2. **Human-readable subfunctions.** A comment labelling a block (`// Step 2: resolve the local day`, `// --- Sections ---`) means the block wants to be a method, or the line below already says it. Name it and delete the label. Sentinel values get names too: `UnlimitedOversize` beats `null // = no cap`.
3. **Unit tests that pin the rule, on both sides of its boundary.** A comment stating a business rule is a rule nothing enforces. Replace it with a pair of tests, one inside the boundary and one outside, named after the rule. A cap of four spare seats becomes "offers a table four seats over the party size" and "rejects a table five seats over", not `// max 4 spare seats`. The pair is the point: a single happy-path test documents a case, whereas the pair documents the limit and fails the day someone moves it. A comment goes stale silently.
4. **Integration/E2E tests for rules that only exist across a boundary.** Same idea one level up. A rule that only shows up end to end (an archived location staying out of `RestaurantDto`, a hold surviving into `POST /api/bookings`, a settings round-trip clearing a field) gets a spec, not a paragraph above the code.
5. **Whatever 1–4 can't reach.** Hidden constraints, upstream bugs, production-incident history, protocol requirements, reachability arguments for coverage suppressions. These stay, but keep them tight: state the constraint, not its biography. "Consolidates the check previously duplicated across four services" is biography; the reader needs the invariant, not the changelog.

Tests augment the rule rather than merely restating it: the rule becomes executable, and the boundary that prose only asserted is now enforced. What is left over after the rule is pinned (a threat model, an incident, an upstream bug) is rung 5 and can stay, but it should be the residue, not the rule written twice.

### Point at the test that carries the rule

When rung 3 or 4 is what replaced a comment, leave a link to the test so the rule stays findable from the code it governs. Use the form each toolchain understands:

- **TypeScript**: a markdown link in JSDoc, path relative to the file. VS Code renders it clickable on hover:

  ```ts
  /**
   * @see [walkIn.test.ts](../__tests__/utils/walkIn.test.ts) — pins that a
   * per-day walk-in flag closes only that day.
   */
  ```

- **C#**: `<seealso>` naming the test method. `cref` can't reach `OpenRestoApi.Tests` (the reference points the other way), so the name goes in the tag body and the checker resolves it:

  ```csharp
  /// <seealso>RestaurantTests.IsPausedFor_BlocksSittingInsideWindow</seealso>
  /// <seealso>RestaurantTests.IsPausedFor_AllowsSittingAfterWindow</seealso>
  ```

Say which rule the test pins, not just that one exists. A bare `@see` is noise.

`npm run check:doc-links` (run in CI by the `doc-links` job in `ci.yml`) fails on a `@see [name](path)` whose file is missing and on a `<seealso>` naming a method that no test class declares. Without it a renamed test rots the link silently, which is the same staleness problem the comment had.

### What this does not license

`<summary>` on a public domain property whose meaning is a data format (`OpenDays` being comma-separated ISO day numbers, `OpenHoursJson`'s shape) stays — that is rung 5 constraint documentation, not narration. Coverage and analyzer suppressions keep their justification (`[ExcludeFromCodeCoverage]` reasons, `#pragma warning disable` rationale). What goes is the summary that restates the signature, the block label, and the changelog entry about which method the code used to live in.

## Architecture

Three-container stack: **Nginx** (`:5062`) → routes `/api/*` to **ASP.NET Core** (`:8080`) and `/*` to **Expo/React Native** (`:8081`). A shared Docker volume (`media_data`) serves uploaded images at `/media/`.

### Backend — Clean-ish layered architecture

Four projects, each referencing only the one below it: `OpenRestoApi` → `OpenRestoApi.Infrastructure` → `OpenRestoApi.Core` → `OpenRestoApi.Domain`. Namespaces are unchanged from when they were folders of one project (`OpenRestoApi.Core.Domain`, `OpenRestoApi.Core.Application.*`, `OpenRestoApi.Infrastructure.*`), so the entities in `OpenRestoApi.Domain` still live in `OpenRestoApi.Core.Domain`.

```
OpenRestoApi/                  # Web host: Program.cs, DI wiring, appsettings, Dockerfile
├── Controllers/               # Thin HTTP layer — validate auth, call services, return DTOs
└── Extensions/                # ServiceCollectionExtensions (DI registration), DatabaseExtensions
OpenRestoApi.Domain/           # Plain C# entities (Restaurant, Booking, Table, Section, …) and the pure rules they
                               # call (OpeningHours, WalkInPolicy, TurnTimes, BookingDuration, ServiceWindowHelper, …)
OpenRestoApi.Core/
└── Application/
    ├── Services/              # Business logic (BookingService, AvailabilityService, AdminService, …)
    ├── Interfaces/            # Contracts for repos, email, clock, holds
    ├── DTOs/                  # Request/response shapes
    └── Mappings/              # Mapperly source-gen mappers (no AutoMapper)
OpenRestoApi.Infrastructure/
├── Persistence/               # EF Core + SQLite (AppDbContext, repositories)
├── Migrations/                # EF migrations (live beside AppDbContext)
├── Holds/                     # In-memory table hold service (singleton ConcurrentDictionary)
├── Email/                     # MailKit SMTP wrapper
├── Cookies/                   # Auth cookie, and the encrypted recent-bookings cookie (DataProtection)
└── Auth/                      # API key auth handler, current-user lookup
```

**Key conventions:**

- **`Domain` references nothing.** No package, no other project: an entity that needs a rule calls one that lives in `Domain` beside it. A helper that both reads an entity and validates a request is split along that line — the pure reader in `Domain` (`OpeningHours`, `WalkInPolicy`, `TurnTimes`), the half that throws `ValidationException` or speaks DTOs in `Application` (`OpeningHoursHelper.ApplyOpenHours`/`ResolveWeek`, `WalkInHelper.NormalizeWalkInDays`, `TurnTimesHelper`), since `ErrorCodes` and the DTOs are API concerns. A doc `cref` from `Domain` to an `Application` type cannot resolve, so name it in `<c>` instead.
- **`Core` never references `Infrastructure`.** Pure code that `Core` needs lives in `Core` (the wallet pass builders, `EmailTemplateBuilder`); anything that does IO or wraps a framework service sits in `Infrastructure` behind an interface in `Core/Application/Interfaces` (`ICredentialProtector`, `IWalletCredentials`, `IMediaStore`). The project references enforce this at compile time. `Core` also has no ASP.NET dependency, only the `Microsoft.Extensions.*` abstractions (`ILogger`, `IOptions`, `IConfiguration`, `IHostEnvironment`), so anything that needs `HttpContext`, `HttpResponse` or `IWebHostEnvironment` belongs in `Infrastructure` or the web project.
- **Infrastructure's `internal` types reach the web project through `InternalsVisibleTo`** (declared in `OpenRestoApi.Infrastructure.csproj`), because `ServiceCollectionExtensions` registers them. CustomAccessibility rejects any internal type used from another assembly unless it carries `[ExternalAccessAllowed]` (error CACC001), so a new internal type registered in DI needs that attribute alongside its `[OnlyAccessibleBy]`.
- All `DateTime` values are stored and passed as **UTC**. EF Core value converters enforce this globally in `AppDbContext`. Restaurant-local times are converted using the restaurant's IANA `Timezone` field only at display/availability-calculation time.
- `OpenDays` is a comma-separated string of ISO 8601 day numbers (`1`=Monday … `7`=Sunday).
- **Per-day opening hours**: `Restaurant.OpenHoursJson` (nullable JSON keyed by ISO day, e.g. `{"6":{"open":"11:00","close":"23:00"}}`) overrides `OpenTime`/`CloseTime` per day; resolve with `OpeningHours.GetHoursForDay` (in `Domain`; validating an update is `OpeningHoursHelper.ApplyOpenHours`). `OpenDays` stays the canonical open/closed toggle. When an update sends identical hours for all 7 days they collapse back to `OpenTime`/`CloseTime` and `OpenHoursJson` is cleared. The API exposes a resolved 7-entry `openHours` list on `RestaurantDto`; the frontend mirrors the fallback logic in `utils/openingHours.ts`.
- **Turn times by party size**: `Restaurant.TurnTimesJson` (nullable JSON array, e.g. `[{"minSeats":1,"minutes":60},{"minSeats":5,"minutes":120}]`) sets a sitting length per party size; a party gets the rule with the largest `minSeats` at or below its size, and below every rule falls back to `DefaultBookingDurationMinutes`. `BookingDuration.For(restaurant, seats)` is the one resolver, and every path that decides a **new** sitting's length goes through it: booking create (single, group, auto-assign), admin create, availability (per request, since it is fetched per `seats`), holds, `TableAutoAssigner`, waitlist seat and `WaitEstimator`. A read about an **existing** booking uses its stored `EndTime` (`BookingDuration.ResolveEnd`), so a booking keeps the length it was taken with. `HoldEntry.DurationMinutes` stores each hold's own length, because two holds on one table can now be for different party sizes; `IsTableHeld` measures an existing hold by its own length and the caller's window by the length passed in. The frontend mirrors the ranges in `utils/turnTimes.ts` for display only.
- **Booking status is a second axis beside `IsCancelled`, not a replacement for it.** `Booking.Status` (`Booked` → `Arrived` → `Seated` → `Finished`, or `Booked` → `NoShow`; stored as text) records the floor, and `IsCancelled` stays the withdrawal flag every query already filters on. Moves go forward only (`Booking.NextStatuses`), a no-show only once the sitting has started (with `CancellationGraceMinutes` of skew), and a cancelled booking takes none; the one way back is undoing the last move within `Booking.StatusUndoWindow`, which `PreviousStatus`/`StatusChangedAt` make possible. **Finishing or a no-show frees the table by shortening `EndTime` to now**, never lengthening it, with the old end kept in `OriginalEndTime` for the undo; that is why nothing in availability, holds, conflict checks or the waitlist needed to learn about statuses. The server hands the client `nextStatuses` and `undoStatus` rather than the client re-deriving the rules. No-show history (`previousNoShows`) is counted per email at read time, never stored, so the GDPR purge covers it.
- **Walk-in-only locations**: `Restaurant.WalkInOnly` (bool) disables the whole online booking flow; `Restaurant.WalkInDays` (comma-separated ISO days, same format as `OpenDays`) disables it per-day. Resolve with `WalkInPolicy` (validating `WalkInDays` on write is `WalkInHelper.NormalizeWalkInDays`); the frontend mirrors the logic in `utils/walkIn.ts`. Walk-in-only locations stay publicly listed — `POST /api/bookings` and `POST /api/holds` reject, `/api/availability` returns an empty slots list, and the UI shows a walk-in notice instead of the booking CTA. Admin-recorded bookings (`AdminService.CreateBookingAsync`) are intentionally exempt so staff can still log walk-ins. **Per table**, `Table.WalkInOnly` holds a table back for the door every day: availability, `TableAutoAssigner` (unless the caller passes `includeWalkInOnly`, which only the waitlist does), explicit bookings and holds all skip or refuse it (`table.walk_in_only`, 409), and a combinable group with a walk-in-only member is held back with it (`TableGroup.HasWalkInOnlyMember()`), since booking the group would take the table. The booking form filters the same way through `onlineSections`/`onlineGroups` in `utils/walkIn.ts`. The walk-in waitlist opens in the Locations page's booking panel (`BookingDrawer` with `waitlist` set, rendering `WaitlistPanel`), from the card's Join waitlist button or the walk-in notice, and the guest's ticket ref is kept per location in storage (`utils/waitlistTickets.ts`) so reopening the panel shows the ticket. My Bookings (`LookupScreen`) shows those tickets above the lookup and apart from it (`ActiveWaitlistTickets`), and only while they are live: a ticket that has been seated, left, expired or is unknown to the server renders nothing and is forgotten, so without a live ticket there is no waitlist on the page at all. `/waitlist/[ref]`, the "table ready" email's link, is that screen with the linked ticket added, the way `/booking-confirmation/[bookingRef]` is with a booking. The "table ready" push reuses the booking-reminder plumbing (`GuestPushSender`, `pushRegistration.ts`) but stores its one device on the entry itself (`WaitlistEntry.Push*`, `PUT /api/waitlist/{ref}/push`, validated by `PushEndpointValidator`): a ticket gets one message, so there is no subscription table, and closing or expiring the entry clears the address. The join form's `WaitlistPushOptIn` registers the device on press, because a browser only prompts in answer to one, and attaches it right after the join succeeds.
- **Cover pacing**: `Restaurant.MaxCoversPerSlot` (null is no cap) limits the seats of online bookings **starting** in one slot, a slot being one `BookingSlotIntervalMinutes` step of the availability grid. `CoverPacing` is the one implementation: `Remaining` for availability (which closes a slot the party would overfill) and for `BookingService` create (re-checked at write time, `booking.pacing_full`, 409, with `cap`/`remaining`/`time`), and `SlotStartUtc` to floor an off-grid time onto the grid anchored at the service's opening, so a client posting 19:10 is counted in the 19:00 slot. Every non-cancelled booking counts toward the total, but admin create and the waitlist are exempt from the check, the same exemption walk-ins get. A hold does not reserve covers, so two guests can race for the last seats and the loser gets the 409. The cap is per interval, not per hour: a 15-minute location gets a finer cap than a 30-minute one. `AdminOverviewDto.TodayPacing` reports today's covers per slot for the dashboard from the same grid.
- **Contact info lives at two levels**: `Restaurant.PhoneNumber`/`EmailAddress` (per-location) override `BrandSettings.PhoneNumber`/`EmailAddress` (global default), resolved **per field** so a location that lists only a phone still inherits the global email. Both sides normalize through `ContactFields` (blank clears, trim, caps from `ContactLimits`); the frontend mirrors the resolution in `utils/contact.ts`. `SocialLink` is deliberately global-only and stays the footer + last-resort contact mechanism.
- **Pausing bookings is scoped to the window, not to the book**: `Restaurant.BookingsPausedUntil` closes the sittings that _start_ inside it, so a pause is "stop seating new arrivals for the next X hours" rather than "stop taking bookings at all until X". `IsPaused()` answers "is a pause running" (badges, the admin overview count); `IsPausedFor(bookingUtc)` is the gate every booking path uses — `BookingService`, `HoldPolicyService`, and `AvailabilityService`, which evaluates it **per slot** rather than once per request. A pause check placed before the requested date is normalized to UTC is the bug this replaced. Rejection wording comes from `PauseHelper` so the booking and hold paths say the same thing.
- **A location's website is server-rendered HTML, not an Expo page.** `RestaurantSite` (one row per location, `RestaurantId` unique, cascade) holds only what the location does not: slug, theme, tagline, logo/cover URLs, gallery and social links as JSON columns (`SiteContent`), and the legal identity. Name, address, hours, phone, e-mail and menus are read from the location at render time, so there is nothing to sync. `GET /r/{slug}` (`PublicSitesController`, outside `/api`, nginx routes `^/(r/…|sitemap.xml|robots.txt)$` to the backend) returns one self-contained document built by `SitePageRenderer` from a `SitePageModel`, which `SiteService` resolves (per-field contact fallback to the brand, `OpeningHours.GetHoursForDay`, `MenuService.GetPublishedMenuViewsAsync` — the same filters as the QR page). Why not React: no bundle on an old phone, real HTML for crawlers and previews, and a future custom domain only needs a Host-based lookup next to `FindLiveAsync`. Things easy to break: (1) **nothing leaves the origin and nothing executes** — one inline stylesheet, system fonts, no script but the `ld+json` data block, and the CSP (`default-src 'none'; img-src 'self'; style-src 'sha256-…'`) is derived from the stylesheet's hash, sent as a header *and* a `<meta>` (the admin preview is an `iframe srcDoc`, which has no headers; `frame-ancestors` is header-only, a browser ignores it in a `<meta>` and logs a warning), a sold-out dish is greyed by the `--muted` token and **never by opacity**, which would defeat the contrast the palette test pins (`SiteThemesTests.Css_GreysASoldOutDishWithTheMutedColour_NeverWithOpacity`), and the legal notice admits the technical access logs rather than promising to collect nothing; every text is escaped by `E()` (the five characters, not `WebUtility.HtmlEncode`, which entity-encodes every accent), every URL is checked before it is written (`SiteFormat.IsSecureUrl` for social links, `/media/` prefix for images), and JSON-LD goes through the default JSON encoder so a field cannot close the script block; (2) **unpublished, unknown, malformed-slug and archived-location all answer the same bare 404 page**, and a published site on a location that is archived and then restored comes back as it was; (3) **publication needs a legal name, a company number, a contact e-mail and a public address for the instance** (`SiteFields.MissingForPublication`; the last because `GetWebsiteUrl` falls back to the dev server and a canonical link must never name it), the legal fields also enforced on later edits of a live site, never on unpublish (an edit is not blocked by the instance losing its address); (4) the booking button is `/r/{slug}/reserver`, a 302 to `/locations/{id}` (or back to `#contact` for a walk-in-only location), so the HTML holds no internal id; (5) uploads pass type, size (6 MB) and magic-byte checks, then `SiteImageProcessor` (Magick, declared type picks the decoder, pixel budget checked before decoding) re-encodes them: shrink-only to 1600/1200/480 px, auto-orient, strip all metadata (GPS), JPEG for photos and PNG for the logo, and `SiteService.StoreAsync` names the file with a fresh `PublicTokenGenerator` token per upload, so the public URL carries no id and never needs cache-busting; (6) the colour is the brand's, corrected for contrast by `SiteColors.Readable` per theme (`SiteThemes.PaletteFor`), and `SiteThemesTests` pins every text pair at WCAG AA for every theme × a spread of brand colours; (7) restaurant purge collects the site's picture URLs before the cascade and deletes the files afterwards (`SiteService.GetPictureUrlsAsync`/`DeletePictures`, wired into `AdminService` like the dish photos). Absolute URLs (canonical, Open Graph, sitemap) come from `BrandService.GetWebsiteUrl`. Admin routes are `SitesController` under the `sites` API key scope; the preview endpoint returns HTML and takes `?theme=` to look at another theme without saving.
- **Combinable table groups**: `TableGroup` + `TableGroupMembership` model tables an admin has flagged as pushable-together; a group is a bookable unit alongside individual tables, and `Booking` stays 1:1 with what it reserves (`TableId` XOR `TableGroupId`). Three invariants are easy to break: (1) a member table is **still individually bookable** — grouping only deprioritizes it, so `TableAutoAssigner`/`AvailabilityService` order ungrouped → grouped → group within each capacity rather than hiding members; (2) mutual exclusion between a member's booking and its group's booking is enforced by `IBookingRepository.IsUnitBookedOnDateAsync` and `IHoldService.IsTableHeld` (a group booking stores `TableId = null`, so any table-only conflict check will miss it); (3) `CombinedSeats` must stay in `(largest member seats, sum of member seats]`, and because the memberships→tables FK is `ON DELETE CASCADE`, anything that deletes or resizes a member table must call `RestaurantManagementService.ReconcileTableGroupsAsync` or the group will advertise capacity it can't seat.
- `HoldService` is a **singleton** in-memory store — appropriate for single-instance deployment. Holds expire after 5 minutes, and one client IP may have at most `HoldService.MaxHoldsPerClient` active at once (raised under `Testing`, like the rate limits). If you need multi-instance, swap for Redis.
- The OpenAPI spec (`/openapi/v1.json`) is only exposed when `ASPNETCORE_ENVIRONMENT=Development`. The dev nginx template (`nginx/default.conf.template`) proxies `/openapi/` to the backend for ZAP CI scanning; the prod nginx (`nginx-vps/`) does not.
- **EF migrations with running dev server**: exe is locked, so use `dotnet ef migrations add <Name> --project ../OpenRestoApi.Infrastructure --no-build` from `OpenRestoApi/` (the migrations live in Infrastructure; the web project is the startup project). If obj/ DLLs are stale the generated `Up()` will be empty — write it manually.
- **`dotnet ef migrations add` Roslyn version pin**: `Microsoft.EntityFrameworkCore.Design`'s own dependency on `Microsoft.CodeAnalysis.CSharp.Workspaces`/`Microsoft.CodeAnalysis.Workspaces.MSBuild` resolves to an older version than `Microsoft.CodeAnalysis.CSharp`/`.Common` get bumped to elsewhere in the graph (via `csulpizi.CustomAccessibility`'s own floor requirement) — a split-version Roslyn install that crashes migration scaffolding at design-time with `TypeLoadException: ReduceExtensionMember ... does not have an implementation` (build/test/runtime never hit this path, so it stays silent otherwise). `OpenRestoApi.csproj` pins `Microsoft.CodeAnalysis.CSharp.Workspaces`/`Workspaces.MSBuild` to match the higher-resolved version to unify the chain; these are `PrivateAssets="all"` and confirmed (via `dotnet publish` diff) not to ship in the runtime output. If `dotnet ef migrations add` starts crashing again after an EF Core upgrade, re-check these pins against whatever `Microsoft.CodeAnalysis.CSharp`/`.Common` actually resolve to (`dotnet restore` + inspect `obj/project.assets.json`) and bump them to match.
- **SCRIPTS** - `scripts/` contains dev/ops scripts (seeding, demo reset, admin recovery). They are not part of the production image. Make sure you update them if the DB is changing in a way that would break them (e.g. new required fields).
- **`scripts/demo_data.py` is the single source of truth for seed/demo data.** It declares the dataset and emits SQL (`config` / `bookings` / `media` / `accounts` / `all`); `seed-local.sh` and `purge-bookings.sh` (the demo VPS's 2-hourly reset) are thin wrappers. Add new data here, never inline in a shell script, and when adding a column add it to the dataset too or the demo silently stops exercising it. The dataset deliberately covers every feature flag the product has (per-day hours incl. a past-midnight wrap, both booking-ref formats, all contact-fallback states, 15/30/60 slot intervals, walk-in-only global and per-day, a live walk-in waitlist with parties already seated, a live booking pause, an archived location, the table-oversize cap, named/unnamed combinable groups, and the native menu module — the flagship's English one and a French-language Belgian brasserie, "Brasserie de la Senne Dorée", in euros with a sold-out dish, a "price on request" dish and an unpublished draft, appended last so no other location's id moves and drawing its bookings from `BELGIAN_GUESTS`), each location annotated with the feature it surfaces. `accounts` covers an Owner (no display name) and a Manager (one), so both roles and both display-name branches are clickable. It is **not** part of `all`: it needs an admin password from `ADMIN_EMAIL`/`ADMIN_PASSWORD` or `--settings-file` (never argv, where `ps` would expose it), and it wipes both `AdminCredentials` and `AdminApiKeys` first so neither a visitor-invited account nor a visitor-minted API key survives the reset. The key wipe has to be explicit: the generator runs under `PRAGMA foreign_keys=OFF`, so the `AdminApiKeys` cascade never fires, and because the wipe reseeds credentials from Id 1 an orphaned key's `UserId` lands back on the new Owner and keeps authenticating for its full year. Each section emits its own `BEGIN`/`COMMIT`, so apply `accounts` as a separate batch. Bookings are generated against the rules the server enforces (opening hours, capacity, oversize cap, the table/group mutual exclusion in `IsUnitBookedOnDateAsync`), so seeded rows never conflict and always carry an `EndTime`. **The platform side is seeded too: a suspended location with a 6-month retention (the Belgian ones hold a fixed period, 12, 6 and 12 months, while the seven pre-existing locations hold NULL, so both states of the retention setting show on the platform list), a draft one mid-assistant with a pending invitation whose token is published on purpose (`DEMO_INVITATION_TOKEN`, so a visitor can walk the real sign-up; the reset puts it back), and a demo restaurateur (`Restaurateur` role, a member of the Senne Dorée) created by the `accounts` section, which also deletes memberships and the consent journal explicitly, since the consent rows carry a visitor's e-mail and the cascade never fires under `foreign_keys=OFF`. **Two upcoming bookings deliberately break that rule**, one on a day the flagship no longer opens and one before it now opens: the schedule-conflict panel and its dashboard count only exist for a schedule narrowed after the bookings were taken, so without them the feature is invisible on the demo. A feature whose UI is driven by data state, rather than by a column, needs the state seeded or the demo silently stops exercising it.
- **The demo has two websites.** `SITES` in `scripts/demo_data.py`: the Belgian brasserie's is published and complete (theme, tagline, three social links, full legal notice, logo, cover, four described gallery photos), the flagship's is a draft with no legal identity, so the "what is missing" checklist and the disabled Publish button exist on the demo. Their pictures follow the artwork rule below under `site-<slug>-logo|cover|photo-<n>` (the slug, never the id, so a public URL carries no internal number); a gallery file with no description in `SITES` is not linked, since the site refuses a photo without one. The committed illustrations are in `scripts/demo-media/` (drawn by `scripts/make_demo_site_media.py`; `seed-local.sh` copies what is missing into the media directory, and on the demo VPS the same files belong in `data/media-snapshot/`).
- **Demo artwork is derived from disk, never hardcoded.** `MediaService` writes uploads into deterministic slots (`hero.<ext>`, `location-<id>.<ext>`, `menu-<id>.pdf`), so `demo_data.py config` leaves `ImageUrl`/`HeaderImageUrl` NULL and the `media` section (`--media-dir DIR`) emits UPDATEs for the files that actually exist. That is why an uploaded image survives a reseed, and why a hardcoded path can never point at a missing file. The media step only ever sets a URL, never nulls one, so it composes on top of `config`; a served `menu-<id>.pdf` wins over an external `menu_url` in the dataset. On the VPS, `data/media-snapshot/` is the curated source of truth — drop correctly-named files in there (or upload via the admin UI and re-snapshot) and they appear on the next reset. Anything not in the snapshot is wiped every run on purpose: demo admin credentials are public, so visitor uploads must not persist.
- **Admin push subscriptions are per browser, never per location.** `AdminPushSubscription` is keyed by `Endpoint` alone (unique index), `POST /api/admin/push/subscribe` takes no `restaurantId`, and `BookingNotificationService.SendPushAsync` fans out over `GetAllAsync()` rather than a restaurant's rows. This is not an accident of the schema: an admin account is not scoped to a restaurant, so a subscription registered while looking at one location is owed every other location's bookings too. Scoping it is what made push look "inconsistent" — the two subscriptions on the 7-location demo were both registered against restaurant 1 while bookings landed on 2, 3, 6 and 7, and `[Push] Sending ... to 0 subscription(s)` was the whole of the symptom. The other half of that silence is the per-subscription `catch (Exception)` in the send loop: `WebPush` throws outside `WebPushException` (`InvalidEncryptionDetailsException` for key material it cannot encrypt with), and an escape there aborts the `foreach`, skips every remaining subscriber and leaves `PushSentAt`/`PushError` unwritten. **A per-subscription failure must never take down the batch** — only 410/404 is treated as stale and deletes the row.
- **Migrations run against data, not an empty schema.** SQLite accepts `ALTER TABLE ADD COLUMN` with a non-constant default (`CURRENT_TIMESTAMP`, `CURRENT_DATE`, any parenthesised expression) only while the table is empty; with a single row present it fails with `Cannot add a column with non-constant default`. A fresh install's tables are empty at migration time and every real install's are not, so this shape passes locally, passes CI, and then breaks every upgrade. `AddMultiUserAccounts` shipped it and broke the VPS deploy. To add a column with a non-constant default: add it **nullable**, backfill with `migrationBuilder.Sql`, then rebuild the table (SQLite has no `ALTER COLUMN`) so both paths land on the same definition — see that migration for the pattern. `migration-check.yml` now seeds a row into every table (`scripts/fill-schema-fixture.py`) before applying the new migrations, so this class fails in CI instead of in production.
- **Migration safety invariant**: a new migration's `Up()` must produce an identical schema whether applied to a fresh database or an upgrade from the previous migration. The `migration-check.yml` CI workflow enforces this by generating SQL for both paths, applying them to SQLite, and diffing the schemas. If they diverge (e.g. `EnsureCreated` and `Migrate()` produce different column order or constraints), the check fails. Always verify that `dotnet ef migrations script "0" PREV_MIGRATION` + `dotnet ef migrations script PREV_MIGRATION` together match `dotnet ef migrations script`.
- **Auto-migration on startup**: `DatabaseExtensions.InitializeDatabase` calls `db.Database.Migrate()` with a retry loop before `app.Run()`. Fresh installs and upgrades are both handled automatically — no manual SQL steps needed.
- **Cross-platform image generation**: use `Magick.NET-Q8-AnyCPU` (ships Linux x64 native libs, no apt-get needed). Never add `Svg` (SVG.NET) — it uses `System.Drawing.Common` which is Windows-only in .NET 7+.
- **Default UI locale**: `BrandService.GetDefaultLocale` resolves `Locale:Default` configuration, then `OPENRESTO_DEFAULT_LOCALE` from the environment, validated against `SupportedLocales` (`en`, `fr`, `es`, `de`, `nl`) and falling back to `en` — same shape as `GetWebsiteUrl`. Always populated on `GET /api/brand` as `defaultLocale`. It lives on the backend, not an `EXPO_PUBLIC_*` build arg, because the frontend Docker image is prebuilt for GHCR releases and a self-hoster can't rebuild it just to change language. The Belgian deployment sets `fr` (`deploy/docker-compose.prod.yml`), which is what "French by default" means: the code constant stays `en`.
- **A guest's language travels with their booking.** The create request may carry a `locale`; `BookingService` stores it through `SupportedLocales.Normalise` on the guest paths only (an unsupported value is dropped, never an error), `BookingMapper` ignores the column both ways, and admin-created bookings leave it null. `BookingConfirmationService` turns it into the mail's language with `GuestLanguage.ForEmail` (`fr`/`nl`/`en` keep theirs, `es`/`de` write English, null takes the instance default) and `BookingEmailCopy` holds the words. Month and day names come from fixed tables in `DateFormatter`, never from culture data: the slim images ship no ICU, and a `CultureInfo` lookup there quietly writes English. `GuestReminderCopy` and `WaitlistReadyCopy` carry `nl` too.
- **The public website speaks French or Dutch, negotiated per request.** `SiteLanguage` picks `?lang=fr|nl` (exact), else `Accept-Language` by q-value (bounded header), else `fr`; `SiteCopy` is the one table of fixed strings, `SitePageModel.Language` keeps the renderer a pure function, and `RenderedSitePage.In(language)` re-renders for the other one. The page sets `<html lang>`, `og:locale`, `hreflang` alternates and a no-script FR | NL switch, keeps its canonical free of any query, and `PublicSitesController` sends `Vary: Accept-Language` beside its one-minute cache. The booking redirect forwards `?lang=` only when it is exactly `fr` or `nl`, and the app reads it on arrival (`LocaleContext`, highest priority, saved as the pick).
- **Outward links on the API Keys screen**: `BrandService.GetCliPackageUrl`/`GetApiDocsUrl`/`GetRepositoryUrl` resolve `Links:CliPackage`/`Links:ApiDocs`/`Links:Repository` configuration, then `OPENRESTO_CLI_PACKAGE_URL`/`OPENRESTO_API_DOCS_URL`/`OPENRESTO_REPOSITORY_URL`, then the upstream OpenResto URLs — same shape and same reasoning as `GetDefaultLocale`, and a value that isn't an http(s) URL falls back rather than being rendered as a link. Served on `GET /api/brand` and consumed by `ApiKeyUsageCard`, which offers only the destinations that resolved and keeps its labels generic ("Command-line client", not "openresto-cli on npm") because a fork configures where a link goes, not what it is called. `docs-site/src/content/docs/api/authentication.md` is the guide the default `ApiDocsUrl` (https://docs.openres.to/api/authentication/) points at, so moving or renaming that page breaks the default link.

│   ├── (user)/           # Customer-facing: index (search), book, lookup
│   └── admin/            # Dashboard, bookings, locations, notifications, settings/*

**Key conventions:**

- `EXPO_PUBLIC_API_URL` drives all API calls. In Docker it is `/api` (relative, goes through nginx). In standalone dev it is `http://localhost:5062`. The `buildEndpoint` helper in `BrandContext` normalises both forms.
- **i18n is `i18next` + `react-i18next`**, one namespace (the default `translation`), never `i18n-js` (no React binding — nothing would re-render when the language changes). Locale JSON lives at `openresto-frontend/locales/{en,fr,es,de,nl}.json`, root level and **not** under `app/` for the same reason component styles aren't: Expo Router would turn each into a route. Keys nest `area.screenOrComponent.concept` under exactly six top-level segments (`common`, `booking`, `restaurant`, `lookup`, `admin`, `errors`), named after the concept never the English text; `tests/i18n/parity.test.ts` keeps the files key-identical to `en.json` — except that `nl` is the guest surface only (home, locations, booking, confirmation, lookup, errors, footer) and ships no `admin` subtree, a carve-out the test names (`GUEST_ONLY_LOCALES`) rather than infers, and `i18n/index.ts` gives it the fallback chain `nl` → `fr` → `en` so a Dutch viewer who reaches an admin key reads French, never a raw key — and `types/i18next.d.ts` module-augments `CustomTypeOptions` off `en.json` so a typo'd key at a `t()` call site fails `tsc`. `constants/locales.ts` mirrors the backend's `SupportedLocales.cs`. `LocaleContext` (mounted under `BrandProvider`, since it reads `brand.defaultLocale`) resolves the active locale highest-priority-first: `localStorage["openresto.locale"]` (a supported value only — written by `LanguageSwitcher`) → the device's language (native: `getLocales()[0]`; web: the first entry of `navigator.languages`, then `navigator.language`, whose language subtag is supported, so `nl-BE` is `nl`; `navigator` may be absent in the static export, which skips the step) → `brand.defaultLocale` → `DEFAULT_LOCALE` ("en"). A route that is not for the guest calls `useBrowserLocaleOptOut()` while mounted (the admin layout does) and skips the web step, so the back office keeps following the instance default instead of the owner's browser; the saved pick still wins there. On resolve it calls both `i18n.changeLanguage()` and `setActiveLocale()` from `utils/locale.ts` — the second call is what makes every `utils/formatters.ts` date/time/number formatter follow the UI language instead of the device's. `constants/defaultCopy.ts` now holds only `loadingMessage` (rendered before any locale is known, so it stays hardcoded English on purpose). The one language picker is `components/common/LanguageSwitcher.tsx` (a `Select`, so it inherits `AnchoredPanel` and its listbox semantics) — mounted only in the admin `AdminSidebar` footer, which has no overflow menu of its own. The guest surface instead reaches locale switching through `components/layout/OverflowMenu.tsx`'s Language row, which opens a `ModalCard` listing `SUPPORTED_LOCALES` directly as `role="radio"` rows rather than nesting `Select` (and its own `AnchoredPanel`) inside a `menuitem` — see the "Anything hanging off a trigger" bullet below for why two anchored panels can't be live at once (issue #387). Both write paths call the same `LocaleContext.setLocale`, so the resolution effect and every switcher go through `LocaleContext`'s `applyLocale` helper, which is what stops them from drifting: a switch that called `i18n.changeLanguage` without `setActiveLocale` would flip every string to the new language while dates and numbers kept formatting in the old one, and would still pass a text-based test.
- Availability is fetched per `(restaurantId, date, seats)`. The API returns 30-minute slots with `{ time, isAvailable, availableTableIds, category }`. `PopularTimesPicker` shows only `isAvailable: true` slots; closed days return an empty slots array from the backend.
- Table holds flow: frontend calls `POST /api/holds` → backend validates open hours + pause state + conflict-checks → returns a `holdId` + expiry. The `holdId` must be included in the subsequent `POST /api/bookings` request.
- **Component styles live in a sibling `<Component>.styles.ts` exporting `styles`** — but **never inside `app/`**. Expo Router treats every module under `app/` as a route, so `app/admin/dashboard.styles.ts` becomes the route `/admin/dashboard.styles`, and — far worse — `app/admin/_layout.styles.ts` matches the `_layout` convention and is loaded as a _layout_, re-parenting every sibling route under `/admin/_layout.styles/...` so `/admin/dashboard` stops existing. Nothing catches this: `tsc`, Jest and lint all pass, and only an E2E run against real routing fails. Screen-level styles therefore live in `styles/` (mirroring the route tree: `styles/admin/dashboard.styles.ts`, `styles/user/lookup.styles.ts`); only styles for components under `components/` sit next to their component. The **Route Manifest** CI job (`npm run routes:check`) guards this: it exports the web build, derives the route list from the emitted HTML, and diffs it against `openresto-frontend/routes.snapshot.txt`. Intentional route changes need `npm run routes:update` and the snapshot committed — routes are public URLs, so changing one should be deliberate.
- **Admin settings is a route group, not a page**: `app/admin/settings/` holds one route per concern (`brand`, `email`, `users`, `account`) and an `index` that redirects to `brand`, so `/admin/settings` keeps working for old links. Each route is a thin list of cards inside `SettingsPage` (shared scroll container, title, and the 880px form column); the cards themselves are unchanged and still take the `borderColor`/`mutedColor`/`cardBg` palette from `useSettingsPalette`. `SettingsPage` also takes an optional `aside`, which renders in a sticky right-hand column above `SPLIT_MIN_WIDTH` (1100px) and stacks above the cards below it.
- **The brand route previews the home page live.** `/admin/settings/brand` is five cards (Brand Identity, Homepage Header, Contact & Website, Highlights, Footer) beside a `BrandPreview` aside. Each card owns its own subset of the brand record, which works because `PATCH /api/brand` reads null as "unchanged" and `""` as "clear" — a card must send `""`, never `undefined`, to clear a field it owns (the favicon deselect was broken for exactly this). The preview reads `BrandDraftContext`, not `BrandContext`: cards publish unsaved values via `useBrandDraftPublish`, so a field that only reaches `saveBrandSettings` won't appear until a reload. `BrandPreview` is a static miniature of `app/(user)/index.tsx`; both share their fallback copy (highlights heading/subheading, hero subtitle, "Our locations") through the same `restaurant.home.*` i18next keys, so the two can't drift the way two hand-copied strings could. `users.tsx` waits for `status !== "loading"` before gating on `can()`: an unresolved session has no role, so it would bounce an Owner on a cold load.
- **Editing an existing record autosaves; the admin's settings and locations forms have no Save button.** `useAutosave` (`hooks/use-autosave.ts`) takes `values` (the payload as it would be sent), `saved` (same shape, from the server-backed context) and `save`; `SaveStatus` renders the outcome where the button was. Both are compared serialised, so fresh object literals per render are fine. Four things bite: (1) the context doesn't refetch after a write, so the hook treats its last committed payload as the baseline — reading dirtiness from `saved` alone re-sends forever; (2) `canSave` withholds writes the server would reject mid-keystroke, and every rule it encodes must mirror a real backend one; (3) a pending debounce flushes on unmount, so `save` must close over the right record id; (4) with no button to grey out, a silent withheld write reads as a broken autosave — state the reason instead (`RestaurantInfoForm` derives a `blockedReason` and renders it where `SaveStatus` sits). `saveBrandSettings` returns `AdminMutationResult`, so success is `result.ok`, never a substring check on the message. Undo works on committed state, not uncommitted edits, which is why it replaced Discard: pass `onRestore` and the hook offers a single-level `undo` for `undoWindow` (10s) after a write lands, putting the old payload back into both the form and the server. Supplying `onRestore` is what enables it — without a way to move the inputs back, undoing would write the old values while the form kept showing the new ones and the next keystroke would re-save them. `undo` commits its target as the baseline before restoring, so the restored values aren't detected as a fresh edit and written twice.
- **The menu screens are three admin routes and one public one.** `/admin/menus` (the editor), `/admin/menus/service` and `/admin/qr-codes` (+ `/print`) sit under `app/admin/`; the guest page is `app/menu/{r,t}/[token]`, **outside `(user)`** on purpose (a guest who scanned a code wants the dishes, not the navbar, tab bar and shortcuts, and `tab-layouts.test.tsx` pins `(user)` to its three groups). Things easy to break: (1) the editor keeps one tree per location and patches it with the pure functions in `utils/menuState.ts` as each call lands; reordering is **arrows, not drag-and-drop** (`MoveButtons` + `utils/reorder.ts`, optimistic with a rollback when the call fails); (2) **availability is one call** — `adminSetItemAvailability` — behind the row toggle, the editor's three chips and the service screen, and it is kept out of the dish's autosave and read from the dish at save time, so a stale form can never write back a sold-out toggle pressed elsewhere; (3) the admin's desktop-only wall below 600px has two exceptions, `/admin/login` and `/admin/menus/service` (`utils/adminRoutes.ts`), and the print sheet is always chromeless; (4) the public page opens in French for a viewer with no saved language through `useRouteDefaultLocale` (`MENU_DEFAULT_LOCALE`), which sits below the viewer's own pick and the device, above the brand default, and is not persisted; (5) **QR codes are black on white and generated in the browser** (`utils/qrCode.ts`, `uqr`, correction level Q), never fetched from a service; the address they carry is `brand.websiteUrl` when it is http(s), else the admin's origin (`qrBaseUrl`), and is printed under each code; (6) printing is `QrSheet.web.tsx`, plain DOM with `@page` and mm sizes so the on-screen sheet is the printed one, and `QrSheet.tsx` is a null stub for the native bundle; (7) regenerating a token is the `regenerate:qr-token` capability (Owner), behind a confirmation that says every printed copy stops working; (8) the public filters hide a dish that **declares** an avoided allergen and require every selected diet (vegan counts as vegetarian) — a dish declaring nothing passes, which is why the page says the filters rest on the restaurant's own information; (9) the "Book a table" button goes to `/locations`, because the public response deliberately carries no restaurant id to build a deep link from.
- **"Mon site" is one admin route, `/admin/site`, behind `manage:site` (Owner and Manager).** `components/admin/site/SiteScreen` picks the location with `useAdminLocation` (the same remembered pick as the menu screens) and stacks `SitePublishCard`, `SiteThemePicker`, `SiteSettingsCard` (tagline, address, legal notice), `SiteSocialLinks`, `SiteImagesCard`, `SiteGalleryCard`, with `SitePreview` in the `SettingsPage` aside. Things easy to break: (1) text fields **autosave** through `useAutosave` and the publish switch, uploads, reorder and delete are explicit calls; every mutating call returns the whole `SiteDto`, so the screen replaces its state with it and `missing` is always the server's; (2) `canSave` mirrors backend rules (slug `utils/siteSlug.ts`, tagline 160, the legal fields a live site cannot lose) and states the reason where `SaveStatus` sits; (3) picking a theme previews it first (`GET …/site/preview?theme=`) and saves through autosave with the usual undo; (4) the preview is a **sandboxed `<iframe srcDoc>` with no `allow-scripts`** (`SitePreview.web.tsx`; `SitePreview.tsx` is the native stub, the admin being web-only), fed by an authenticated fetch of the HTML, because an iframe pointed at the API would be refused by the `X-Frame-Options: DENY` nginx sets; (5) a gallery photo cannot be added without its description, and the add control disappears at six; every radio carries `aria-checked` beside `accessibilityState` (react-native-web reads only the former — `SiteThemePicker`, `LocationPills`); (6) social-link URLs are checked with a regex, not `new URL(x).protocol`, which throws in React Native's polyfill. `moveId` in `utils/reorder.ts` is generic so photo tokens (strings) reorder like ids. E2E: `e2e/site-admin.spec.ts` (the screen) and `e2e/site-public.spec.ts` (the page through nginx); `scripts/capture-site-screens.mjs` makes the sprint captures and `scripts/serve-local-stack.mjs` stands in for nginx without Docker.
- **Anything hanging off a trigger is `components/common/AnchoredPanel`.** React Native has no popover primitive, which is why the app grew four hand-rolled ones (issue #348). The shared shell owns the `Modal`, the dismiss backdrop, the position, focus in and out, and forwarding keys; the geometry is `utils/anchoredPanel.ts` (flip up when the list would run off the bottom, clamp at a screen edge, `align: "end"` for a panel wider than its trigger) and the tracking is `hooks/use-anchor-tracking.ts`, which re-measures on scroll and resize. Web hangs the panel off the trigger; native, and any web trigger that reports no box, gets a centred sheet. Two rules are easy to break: the panel is the **one** focus target and navigates by `aria-activedescendant`, so its rows carry `tabIndex={-1}` and never take focus themselves (fifty rows in the tab order is not a control anyone gets past); and `role` is what the panel _is_, so a list of values is a `listbox` of `option`s under a `combobox` trigger and only a list of commands is a `menu`. Key handling is `utils/listboxKeys.ts`, a pure resolver, so every key is pinned by a unit test rather than by a browser. React Native's `Role` union omits `listbox`, hence `LISTBOX_ROLE` in `utils/webProps.ts`, which is also where the `aria-*` and `onKeyDown` props RNW forwards but RN does not type live, so no call site needs `as any`.
- **Buttons are one primitive, two layouts.** Every button in the app is `components/common/Button` — there is no second way to draw one, and a `Pressable` styled to look like a button is a bug. Its two axes are independent: `variant` is weight (`primary` filled / `secondary` outlined / `ghost` bare) and `tone` is meaning (`brand` / `danger` / `warning` / `success` / `neutral`), so "Remove image" and "Yes, delete permanently" are the same destructive control at two weights rather than two hand-rolled styles. `variant="danger"` is a kept alias for filled-destructive. Sizes: the admin uses `size="md"` (44px, the WCAG 2.5.5 target) for every action; `lg` is for a focused form's own submit (login, the booking form); `sm` is the row scale. Buttons group through `components/common/ButtonRow`, whose children keep their natural width — it wraps rather than using a breakpoint, so a cluster too wide for its card drops to a second line instead of one button stretching full-width while its neighbour shrinks. Source order is reading order: **dismissing and destructive actions first, the primary last**, and a cluster gets **one** filled button. `fullWidth` is opt-in and reserved for a form's single submit. **Row-level actions** (a list row's trailing cluster) are `components/common/RowTextButton` — a named pill, never a bare glyph, because the admin runs on tablets for staff who are not in it daily; it reaches 44px through hitSlop so rows stay dense. Icon-only controls (`IconButton`) are for the handful of universally-read glyphs in genuinely constrained chrome — a modal close, a reorder arrow, a date-bar chevron — and always carry an `accessibilityLabel`.
- **A filled button means create or commit, never "save".** Autosave took "save" away from field edits, leaving the filled button one honest meaning: it makes something new, or does something you can't walk back. A list's standing create CTA is `AddRow` (collapsed to one `Add X`, expanded to fields plus Cancel/Add) in `<ButtonRow align="start">`, flush with the rows it appends to. A form serving both new and existing rows (`SocialLinkEditForm`, `HighlightsCard`'s editor) takes `isNew` and labels the commit **Add** or **Save** to match; a create labelled "Save" is the bug this rule catches. Deliberate explicit-press carve-outs: `SecurityCard` (the press is the confirmation for a credential change), `EmailSettingsCard` (`sendBookingConfirmations` ships with the SMTP credentials and `handleTest` saves before testing, so a debounce would put half-typed credentials on the wire and test against them), `BookingDetailPopup` and `DangerZone` (guest-visible or irreversible), and `TableRow` (its Cancel genuinely reverts).
- **Chrome favicon caching**: never update `<link rel="icon">` href in-place — Chrome ignores it. Remove all existing favicon links then append a fresh `<link>` element to force re-read.
- **PWA manifest URL**: must remain a same-origin HTTP(S) URL. Replacing `<link rel="manifest">` href with a `blob:` URL silently breaks Chrome's PWA installability check.
- **SW cache versioning**: bump `CACHE_NAME` in `public/sw.js` on every deploy that changes `public/manifest.json`, otherwise browsers serve the stale cached manifest.
- Tab favicon (SVG data URI via `injectBrandFavicon`) works in standalone dev. PWA install icon requires Docker — nginx must proxy `/api/brand/pwa-icon-*.png` to the backend.
- `app/+html.tsx` is Expo Router's HTML `<head>` template for static output mode — favicon link, manifest link, and SW registration script all live here.
- **Cross-platform scroll-to-element**: to smoothly scroll a `ScrollView` to a specific child after it appears, use two paths: on web call `(ref.current as unknown as HTMLElement).scrollIntoView?.({ behavior: "smooth", block: "start" })`; on native measure the child against the scroller's **content view** — `(scrollRef.current as unknown as { getInnerViewRef?: () => ... }).getInnerViewRef?.()` — and then `childRef.current.measureLayout(content, (_x, y) => scrollRef.current?.scrollTo({ y: Math.max(0, y - 16), animated: true }), () => {})`. Two things are load-bearing: measuring against the content view and not the scroller gives an offset into the content rather than a viewport position, which moves as the list scrolls; and it must be that **ref**, never a `findNodeHandle` number, which the New Architecture rejects. `utils/scrollIntoView.ts` is the one implementation — call it rather than rebuilding either half. Wrap in a `setTimeout` of ~150 ms so layout settles before measuring. See `components/restaurant/LocationsScreen.tsx` (scrolling to a deep-linked/expanded location) . The booking sheet's scroller (`BottomSheetScrollView`) exposes no content view at all, so a field inside it cannot be measured this way — `components/common/KeyboardAwareScroll.tsx` measures against the window instead, see below. `/lookup` used to be the worked example here but dropped its auto-scroll when the found/cancelled/past result moved into a `SlidePanel` beside the form — the panel is already in view on desktop and the bottom sheet owns the viewport on compact, so there is nothing left to scroll to.
- **Lint `no-explicit-any`** (oxlint, `.oxlintrc.json`, replaces ESLint): never cast with `as any`. When you need to access a DOM method unavailable on the RN type, use `as unknown as HTMLElement` (or the appropriate DOM type) instead. React Compiler-only `react-hooks/*` rules (e.g. `set-state-in-effect`) have no oxlint equivalent yet and are no longer enforced.

### Native guest app (built by the self-hoster, issue #388)

The guest routes under `app/(user)/` also build as a native iOS/Android app that a self-hoster publishes under their own store accounts against their own instance — `docs-site/src/content/docs/guides/native-app.md` is the walkthrough. Upstream never publishes a binary and CI never runs a native build; the `native-bundle` job only bundles the JS for both platforms (`expo export --platform ios --platform android`), which is enough to catch a web-only import reaching the guest routes. Admin stays web-only: `app/admin/_layout.tsx` redirects to `/` off web. The pieces that are easy to break:

- **Per-publisher config is generated, never committed.** `npm run native:init` (`scripts/native-init.mjs`, logic in `scripts/lib/native-init.mjs`) reads the instance's `GET /api/brand` and writes `openresto-frontend/native/` — `app.native.json`, `icon-ios.png`, `icon-android-foreground.png`, and `.well-known/{apple-app-site-association,assetlinks.json}`. `app.config.ts` merges `app.native.json` when it exists (bundle id, package, scheme, deep-link host, colours, `extra.apiUrl`, `extra.eas.projectId`) and is byte-for-byte the old config when it does not, so the web image is unaffected. `native/` is gitignored; `.easignore` exists solely so EAS uploads it anyway, and because EAS reads `.easignore` _instead of_ `.gitignore`, `tests/easignore.test.ts` fails if the two drift. Re-runs of `native:init` merge over the existing `app.native.json`, so adding `--project-id` or a fingerprint later needs only that flag.
- **The API base is still a build-time constant.** `api/client.ts`'s `configuredApiUrl` reads `EXPO_PUBLIC_API_URL` first (inlined by Metro; `/api` in the Docker web build) and falls back to `Constants.expoConfig.extra.apiUrl`, which `app.config.ts` bakes in from `serverUrl`. There is deliberately no runtime server picker: the person building owns the server, and one generic client would put upstream on the hook for every self-hoster's store listing.
- **Storage is a platform split behind one sync API.** `services/storage.ts` (web, localStorage) and `services/storage.native.ts` (`expo-sqlite/kv-store`, synchronous methods) share `StorageService`'s string shape, so `usePersistedState`, `ThemeContext` and `LocaleContext` stay synchronous. The web bundle must never import `expo-sqlite` (it would want wasm) — Metro's `.native.ts` resolution is what keeps it out.
- **Recent bookings are client-held off web.** `GET /api/bookings/my-recent` reads an HttpOnly cookie a native app never has, so `utils/bookingCache.ts` keeps the same `CachedBooking` shape in `StorageService` on native (`rememberBooking` after `createBooking`, a no-op on web) and reads it back in `fetchCachedBookings`. The cookie stays the web source of truth.
- **Server-relative media URLs are joined onto the server off web.** The API hands out uploads as paths (`/media/location-3.jpg`, `/media/menu-3.pdf`) that the browser resolves against its own origin; a native app has none, so `utils/serverUrl.ts`'s `resolveServerUrl` prefixes them with the configured API base minus `/api` (the host nginx serves `/media/` from) and passes absolute URLs and web through untouched. Every `expo-image` source and `Linking.openURL` of an API-supplied URL goes through it; the home hero renders through `expo-image` off web for the same reason (the web `<img>` is a DOM element React Native cannot mount).
- **Calendar export shares the ICS text, not the delivery.** `utils/calendar.ts`'s `buildIcs` is pure; web downloads a Blob, native writes the file with `expo-file-system` and hands it to `expo-sharing`. Outbound URLs go through `Linking.openURL` off web (`window.open` on it); `window.confirm` is wrapped the same way for the oversize-table prompt.
- **App icons for the stores are separate endpoints, not a wider `pwa-icon-{size}` allow-list.** `GET /api/brand/app-icon-ios.png` is 1024², opaque, square (App Store Connect rejects alpha, and Apple applies its own corner mask, so the PWA's rounded rect is exactly wrong); `GET /api/brand/app-icon-android-foreground.png` is 432² with a transparent background and the glyph inside the 66/108 safe zone. Both 404 until a brand icon is chosen, same as the PWA icons; `--icon`/`--android-foreground` on `native:init` substitute real artwork locally instead of adding an upload slot.
- **`.well-known` is served by nginx from a bind mount**, not the frontend image: `location ^~ /.well-known/` in `nginx/default.conf.template` forces `application/json` (AASA has no extension) and `docker-compose.release.yml` mounts `./well-known` next to the compose file. That is what lets a self-hoster on prebuilt images add Universal Links / App Links without rebuilding anything. The generated files open the guest paths and exclude `/`, `/admin` and `/api`.
- **The server knows its native clients only in aggregate.** Off web, `api/client.ts` sends `X-OpenResto-Client: <platform>/<version>` (never on web, where it would add a CORS preflight to every call). `NativeClientIdentity.TryParse` accepts only `ios|android` and strict `major.minor.patch`; anything else is ignored silently. `NativeClientStatsCollector` (singleton, in memory) is flushed by `NativeClientStatsWorker` every minute into `NativeClientStats`, one row per (platform, version, day), pruned after 90 days. No IP, device id or user agent is ever stored, which is why the table can sit under `brand:read` and outside the audit-trail PII rules. The header is unauthenticated and every well-formed version is a new key, so the counting is bounded twice over: the middleware runs **after** `UseRateLimiter` so a refused request is never counted, `NativeClientStatsCollector.MaxBuckets` caps what a flush window may open, and `NativeClientStatsRepository.MaxVersionsPerPlatform` caps the versions the table tracks — a version already tracked keeps counting past either cap, so the builds in use are never the ones dropped. `GET /api/admin/native-app/status` (`NativeAppStatusService`) is what `/admin/settings/native-app` renders: the readiness checks (https, brand icon, privacy policy, the two `.well-known` fetches) plus that summary. **The probe is an SSRF primitive unless every hop is guarded**, because the "public address" it fetches is `BrandSettings.WebsiteUrl`, writable by anyone with `brand:write`: `NativeAppChecks.TryBuildWellKnownUrl` composes the URL from the site's origin (so a query string on the address cannot swallow the fixed path, and a sub-path is rooted the way the verifiers read it), `PublicAddress` refuses `localhost` and private/link-local literals before any fetch and `WellKnownProbe` refuses a host that _resolves_ there, the named `HttpClient` never follows redirects and caps the body, and `BrandService.SaveAsync` holds the URL to absolute http(s) in the first place. `PublicAddress` is the same classifier `PushEndpointValidator` uses, so the two fetch-on-a-caller's-say-so paths cannot drift apart.
- **Two brand fields exist for the stores, not the website.** `BrandSettings.PrivacyPolicyUrl` (both stores refuse a listing without one; the guest footer links it everywhere) and `BrandSettings.MinimumAppVersion` (strict `major.minor.patch`; a native build below it renders `UpdateRequired` instead of the navigator, web never gates). Both follow the brand PATCH contract: null unchanged, `""` clears.
- **Native-only UX splits, all with the web branch untouched:** the theme's "system" preference reads `Appearance` off web and `matchMedia` on it; the device locale sits between the saved pick and the brand default, read from the phone off web and from the browser's language on it (the admin opts out of the latter); language and theme are reachable through `GuestSettingsMenu` because `Navbar`/`OverflowMenu` never render there — the three tab roots (home, locations, lookup) draw with no native header and no swipe-back (`tabRoot()` in `components/layout/GuestTabStack.tsx`), and so does `/booking-confirmation/[bookingRef]` — it is `LookupScreen` with the ref prefilled, so it draws the way `/lookup` does rather than as a detail pushed over the booking form, which is what it already looked like on web under one navbar; `justBooked` therefore reaches only the result panel's wording and the arrival haptic, never the page's own chrome. `ScreenHeading` with `standalone` is the top of each, carrying the title, while the screens genuinely pushed over a root keep the header and its `headerRight`; where there is no header the control comes from `GuestSettingsAnchor`, rendered by `GuestTabStack` **outside** the tab's `Stack` — a copy inside the page (the home hero's corner, `ScreenHeading`'s title row) scrolled away with the content. Its `isHeaderlessGuestRoute` is `tabRoot()`'s question asked from the other side and must stay in step with it: exact for the fixed roots, prefix for the confirmation alone because its ref is a path segment — a looser match would double the control up on `/locations/[id]`, which has a header already. The roots' own titles reserve `SETTINGS_ANCHOR_SLOT` so nothing lands under it; a header-less root pads its own `insets.top`, and **where** decides whether content scrolls under the status bar. `/lookup` pads its scroll **content**, so the form runs under the bar the way the home hero does. `LocationsScreen` pads the column **outside** the ScrollView instead, and must keep doing so: its filter band pins by `stickyHeaderIndices`, and the only way to keep a pinned band clear of the clock is to give it the inset once pinned — which changes a sticky child's height mid-scroll and jumps everything below it by that much, so the list bounces around the pin threshold. Getting Locations edge-to-edge means lifting the band out of the scroller and animating it, not toggling its padding. A screen pushed **under** a header hands the job to the scroll view instead (`contentInsetAdjustmentBehavior="automatic"`, which is also what lets iOS collapse the `headerLargeTitle` `guestHeader()` asks for) — `LocationsScreen` draws both routes and takes `hasNativeHeader` to pick, since doing both at once double-pads the top of the list; `useOnline` (`navigator.onLine` on web, `expo-network` off it) drives `OfflineBanner`; the booking and lookup forms sit in a `KeyboardAvoidingView` off web; party size is a `Stepper` off web and stays a `Select` on it (a list of numbers in a sheet reads as a website's form control, a stepper driven by a mouse is worse than a dropdown), and the stepper walks the **same option list** the dropdown gets rather than carrying its own min/max, which is how the two would start offering different party sizes; the date is the platform's own calendar off web (`@react-native-community/datetimepicker`, inline on iOS and the stock dialog on Android) and stays the listbox in `DatePicker.web.tsx` on it — the system control clamps to a range and cannot disable days inside it, so `openDays`/`unavailableDays` are accepted and unread there and a closed or walk-in-only day is answered downstream by `booking.form.closedDayNotice` and `WalkInDaysBanner` rather than by a day that was never offered; both halves take their window from the one `generateDateOptions`, so the bounds and the labels cannot drift; directions are one pill opening the platform's own maps app (`utils/directions.ts`: the `maps://` scheme on iOS, a `geo:` intent on Android, falling back to the https page if nothing answers) where web offers both; the theme's `overlay` token is transparent on purpose, so no modal surface dims the page on any platform, and `RestaurantCard` drops its open-in-new-tab control there; the booking and lookup sheets pad their bottom by the safe-area inset; Home and Locations take a `RefreshControl`, which bumps a `generation` folded into each card's key so the cards remount and re-ask for availability; the Locations filter bar pins through `stickyHeaderIndices`, so off web the page is three direct ScrollView children (heading, band, list) rather than one `PageContainer` — a fragment would count as one child and pin the wrong thing; the home hero renders a light `StatusBar` over a header photo only while the screen is focused (`useFocusEffect`), since the screen stays mounted under whatever is pushed on top; the booking result's Copy button becomes Share (`Share.share`) off web; and **My booking** stays selected on `/booking-confirmation/*` as well as `/lookup*` because both route files live in the `(bookings)` group (see the tab-bar bullet below), not because anything matches the path.
- **A focused field is lifted clear of the keyboard by `KeyboardAwareScroll`, off web only.** Nothing in React Native does this: `KeyboardAvoidingView` pads the container, the booking sheet's `keyboardBehavior="interactive"` resizes the sheet, and Android's `adjustResize` resizes the window — all three move the _container_, so a form long enough to scroll put the field being typed in behind the keyboard. The shell wraps whichever scroller it is given (`as`), tracks its offset, and publishes one `scrollFieldIntoView` through context; `Input` calls it from its own `onFocus`. Two things are load-bearing. The field is measured with **`measureInWindow`** and compared against the keyboard's own **`endCoordinates.screenY`** — window coordinates on both sides, so it needs no reference to the scroller's content view, which the sheet's scroller does not expose (measuring against that content view is the version that silently did nothing inside the sheet). And the scroll is attempted **both** on focus and again on `keyboardDidShow`, because the two arrive in either order: tapping a field with the keyboard down focuses first, while moving between fields with it already up fires no keyboard event at all. The geometry is `utils/keyboardAwareScroll.ts`, a pure resolver returning `null` for a field the keyboard never reached — scrolling on every focus makes the form lurch as the guest moves between fields — so which case scrolls is pinned by unit tests rather than by a device. Web is a pass-through: the browser does it, and the node keeps exactly the props it had.

- **A booking sheet must dismiss itself before navigating.** `BookingDrawer.handleSubmit` takes the platform sheet's own `dismiss` and calls it once the booking is real, before pushing the confirmation route. The sheet provider is mounted above the navigator (`app/_layout.tsx`), so its portal draws over whatever screen is on top, and the tab bar keeps the Locations screen mounted behind it — navigating without dismissing leaves the booking sheet stacked over the confirmation's own result sheet. Web passes nothing, since navigation there swaps the page out from under the drawer, which is why this only ever showed up on a phone.

- **A sheet on a phone is the platform's, never a hand-rolled one.** `components/common/NativeSheet` (with `components/booking/NativeBookingSheet` for the booking form, which needs fixed detents rather than content sizing) is the shell; a `Modal` + `PanResponder` + `Animated` sheet **does not drag on a device at all**, neither by its body nor by its handle, which is how the lookup result panel shipped with the backdrop as the only way out of it. That machinery is web-only and stays on web, where there is no platform sheet to defer to. `NativeSheet` sizes to its content up to a cap (`maxHeightRatio`, 88% by default, past which the body scrolls inside it) rather than to detents, so a panel that is one short card does not open at three quarters of the display. Two rules come with it: the drag out has to be real (`enablePanDownToClose`, plus a backdrop whose `pressBehavior` is `"close"` and not merely a dim) on any sheet carrying no close button; and everything in the context bullet below applies, since the content renders through the portal.

- **The native sheet reads its context from `app/_layout.tsx`, not from the screen that opened it.** `@gorhom/bottom-sheet` renders sheet content through `@gorhom/portal`, which re-renders the node at the `PortalHost`'s own position in the tree — so every provider mounted above `BookingSheetHost` is visible to the sheet and every provider below it is not. With the host outermost, as it first shipped, the booking sheet read `DEFAULT_BRAND`'s stock teal and `ThemeContext`'s dark default and so ignored both the restaurant's brand colour and the visitor's light/dark pick, on a screen the rest of which was themed correctly. `BookingSheetHost` therefore sits **innermost** of the app's own providers (`BrandProvider` > `LocaleProvider` > `AppThemeProvider` > `BookingSheetHost` > the navigator); `GestureHandlerRootView` inside it still wraps everything that renders UI, since a context provider hosts no gestures. Anything else moved onto the platform sheet inherits the same rule. `tests/app/root-layout.provider-order.test.tsx` pins the nesting, because nothing else fails when it is wrong — the sheet just renders in the wrong colours. The insets follow the same boundary the other way: the host is above the tab navigator, so `useSafeAreaInsets` inside a sheet answers for the **window**, not for a tab's content area, and whatever the sheet puts against its bottom edge owns the gesture inset itself — `DockedBookingSubmit` pads by it, and without that the confirm ran to the physical bottom of the screen with Android's home handle drawn across it.

- **Haptics go through `utils/haptics.ts`, never `expo-haptics` directly.** `selectionAsync`, `impactAsync` and `notificationAsync` are only haptics on iOS: on Android all three drive `Vibrator.vibrate(createWaveform(...))`, a 43–60 ms burst of the ringer motor that is audibly a buzz rather than a tick, and Expo's own docs say not to use them for feedback. The wrapper's three effects — `selection` (moving between discrete choices), `press` (a press landing), `outcome("success" | "warning" | "error")` — keep the iOS generators and route Android through `performAndroidHapticsAsync`, i.e. `View.performHapticFeedback`, the same system haptic composition the platform's own controls use, which also respects the device's touch-feedback setting. Two things are load-bearing: most `HapticFeedbackConstants` arrived in API 30 and the native module **rejects** rather than degrading on an older device, so each effect names a fallback that has existed since API 24; and every call swallows its own failure, because a phone with no actuator must not take a screen down with it. Call sites name what happened rather than which API to reach for, which is what stops the platform split from being re-decided at each one.

- **The guest tab bar is the platform's own, and the route groups are what drive it (#426).** Off web `app/(user)/_layout.tsx` renders `GuestTabs` (`expo-router/unstable-native-tabs`; `GuestTabs.web.tsx` is a `Slot` stub so the Radix web implementation never reaches the web bundle, which keeps `Navbar`/`OverflowMenu`). A tabs navigator cannot host a pushed screen, so every guest route lives in one of three groups — `(home)`, `(locations)`, `(bookings)` — each a route group whose `_layout.tsx` renders `GuestTabStack` (a `Stack` off web, a `Slot` on it) around its `Stack.Screen`s. The group a file sits in is what decides which tab lights up: `booking-confirmation/[bookingRef]` is in `(bookings)`, and the redirect shims that resolve to a location (`book`, `book/[restaurantId]`, `restaurant/[id]`) are in `(locations)`, so a redirect never crosses tabs. **Every shim declares `headerShown: false`** (as `/search` does under `(home)`): it renders only a `<Redirect>`, but it is mounted for a frame first, and a shim carrying a title flashes a header — back arrow and all — on the way through. `book` is also what a cold press on the Locations tab can land on for that frame, since it sorts ahead of the initial route. `tests/app/(user)/tab-layouts.test.tsx` pins that the `(user)` directory holds exactly those three groups, so a route file added outside one fails CI rather than becoming unreachable on a phone. Groups add nothing to public URLs (`routes.snapshot.txt` gained only group-prefixed duplicates), but `(locations)` **must** name `initialRouteName: "locations/index"`: by route order `book` sorts ahead of `locations/index`, and a tab that mounts on the shim sends itself to `/` on launch. Scroll-to-top and pop-to-root on re-pressing the selected tab come from react-native-screens on both platforms, so nothing in JS listens for `tabPress`. Insets are the part that is easy to break: iOS runs the content under a translucent bar and, unless told otherwise, flips the first scroll view it finds to automatic insets, which double-pads a root that already pads `insets.top` and moves the home hero out from under the status bar — so the triggers set `disableAutomaticContentInsets` on iOS only, `GuestTabStack` nests a `SafeAreaProvider` so `useSafeAreaInsets` inside a tab answers for the tab's content area (the bar's height at the bottom on iOS, zero on Android, whose opaque bar the platform pads itself), and every header-less root pads its scroll content by `useTabBarClearance`. A screen pushed under a native header (`locations/[id]`) takes neither — `contentInsetAdjustmentBehavior="automatic"` hands both edges to the scroll view. A `Modal` inside a tab inherits the tab's insets, which is why `SlidePanel`'s sheet mounts its own provider: the sheet covers the bar, so the inset it steps over is the window's home indicator. iOS keeps the system tab bar appearance (no `backgroundColor`/`blurEffect` there) because any of them replaces the iOS 26 liquid glass; Android gets the card surface and the Material 3 pill. None of this is verifiable in CI — the Jest suites pin what each trigger and screen asks for, and a change here wants a simulator on both platforms.
- **Versioning.** The app version is the OpenResto release (`package.json`), unchanged. `ios.buildNumber` / `android.versionCode` are on EAS's side (`appVersionSource: "remote"`, `autoIncrement`) and are deliberately outside `check-release-version.sh`: they move on the publisher's cadence, not the tag's.
- **The hold-expiry warning is local, and never blocks a booking.** A table hold lasts five minutes, and off web `useTableHold` schedules an `expo-notifications` local notification for expiry minus `HOLD_EXPIRY_NOTICE_LEAD_SECONDS` so backgrounding the app does not silently cost the guest the table; the `services/holdExpiryNotice.ts`/`.native.ts` split keeps the module out of the web bundle (Jest maps the bare import to the web file, as it does for `storage` and `pushRegistration`), and web is deliberately inert — a backgrounded tab cannot run the timer and a foregrounded one already shows `HoldStatusBanner`'s countdown. Nothing reaches the server: this is the phone's own scheduler, not the push path above. Three things are easy to break: it **never prompts** — a hold is the guest asking for a table, not for notifications, so it schedules only where permission has already been granted, and the one prompt lives on the confirmation screen's reminder toggle; every failure — permission never granted, a hold shorter than the lead, a notifications module that will not load — returns null rather than throwing, because a guest who cannot be warned must still be able to book; and every path that ends a hold has to withdraw the warning (replaced, refused, released, expired, unmounted), which the generation counter in `cancelExpiryNotice` is what makes safe against a permission prompt that outlives the hold that raised it.

- **Guest booking reminders are keyed to the booking, never the person.** `GuestPushSubscription` holds one push address per (booking, device): an Expo push token from the native app (`GuestPushChannels.Expo`, sent through `ExpoPushClient` to Expo's service, which holds the APNs/FCM credentials so the server never does) or a browser's Web Push subscription (`GuestPushChannels.WebPush`, sent through the same `IWebPushClient` + `VapidSettings` the admin notifications use). `GuestPushSender` is the channel switch. **A push address is validated before it is stored** (`PushEndpointValidator`, on both the guest and the admin subscribe): a Web Push endpoint is a URL the worker POSTs to on a timer, and the guest opt-in needs only a booking reference and an email, so an unchecked one is a request the server makes wherever a diner points it — it has to be https on a public host (`PublicAddress`), and because a name can still resolve inside the deployment, the `IWebPushClient` is built on `PublicOnlyConnector`, whose `ConnectCallback` resolves the host, refuses any private address and opens the socket to exactly the addresses it checked (no proxy, no redirects); `GuestPushSender` turns anything the send throws into that subscription's failure, since an escape would end the reminder run for every guest after it; an Expo token only has to be the shape Expo mints, since it travels in a body to Expo's own API. Opt-in and opt-out are the two by-ref guest endpoints on `BookingsController` (`POST`/`DELETE ref/{ref}/reminders`), which take the reference-plus-email pair, answer the identical 404, and sit on `BookingLookupPolicy` like lookup and cancel, so `BookingRefEndpointRateLimitTests` lists them. `GuestReminderWorker` runs `GuestReminderService.SendDueRemindersAsync` every minute; which reminder a device is owed is `ReminderSchedule.DueLead` (pure, pinned both sides): a lead window (`GuestPush:ReminderLeadHours`, default `24,2`) is sent once its opening time has passed, only if it opened after the guest opted in (booking tomorrow's table must not produce a "24 hours to go" push seconds later), only if shorter than the last lead sent, and when several are open the shortest wins. A stale address (Web Push 410/404, Expo `DeviceNotRegistered`) deletes the row; any other failure records the lead so a refusing provider is not retried every minute. Rows cascade with the booking (the GDPR purge covers them), are pruned once the sitting has started or the booking is cancelled, and `demo_data.py` wipes the table explicitly because `foreign_keys=OFF` skips the cascade. Copy is `GuestReminderCopy`, in the four UI locales and the restaurant's timezone; the frontend's `pushRegistration.ts`/`.native.ts` split keeps `expo-notifications` out of the web bundle (Jest maps the bare import to the web file, as it does for `storage`), the device remembers what it registered in `utils/reminderRegistry.ts` because the server cannot answer "is this device subscribed" without the address, and `useBookingReminder` never prompts until the guest presses the toggle.
- **Wallet passes are built from the booking, signed with the self-hoster's own issuer, and never stored.** `WalletSettings` (`Wallet__Apple__*`, `Wallet__Google__*`) name the files; `WalletCredentialStore` loads them once per process and treats a file that fails to load as "not configured" (logged once, button hidden) rather than a 500 per guest. `ApplePassBuilder` writes a generic pass (`pass.json`, the icon set from `PwaIconGenerator`, a SHA-1 manifest, a detached PKCS#7 signature with the WWDR intermediate in the chain) and `GoogleWalletLinkBuilder` an RS256 "save to wallet" JWT with the class inlined so no Google API call ever happens; both take a `PassContent` the `WalletPassService` resolves in the restaurant's timezone, with the manage link from `BookingLinks.Confirmation` (shared with the confirmation email and the reminder push so the three cannot drift). A cancelled booking gets a 409, since Wallet has no way to learn of a later cancellation. `GET /api/brand` advertises `wallet.apple`/`wallet.google` so `WalletActions` offers only what exists, one pill on a phone (its own platform) and both on web; the native Apple path downloads the `.pkpass` to cache and hands it to the share sheet, where Add to Wallet is the first row. `NativeAppStatusService` reports both issuers as `skip` rather than `fail` when unset because they are optional.
- **Not built yet, and separable:** the iOS 4.2 submission probe. Android needs none of the above to ship.

### Auth model

**Admin users** — `AdminCredential` holds one row per user (PBKDF2 hash, per-user PVQ, `Role`, `IsActive`); the table name predates multi-user support and stays put so the migration is additive. `POST /api/admin/auth/login` looks the account up by email and mints a JWT carrying `sub` (user id), email, and the account's own role.

- **Roles live in one allow-list** (`OpenRestoApi.Domain/UserRoles.cs`): `Owner` and `Manager`, plus `Admin` — the claim value minted before multi-user existed, honoured only so 30-day tokens issued by an older build keep working. No user row ever carries it.
- **Gating goes through named policies** (`AuthPolicies` + `AddAuthorization` in `ServiceCollectionExtensions`), never raw role strings on controllers. `RequireAdmin` = any admin; `RequireOwner` = user management. Adding a role, or swapping roles for permission claims, is a change to those two places.
- **The user id is the identity.** `ICurrentUserService` reads it off the claims and `CurrentUserResolver` turns it into the row; email is only a fallback for id-less legacy tokens. Self-service (change password/email, PVQ setup) always targets that row — never "the" credential.
- **Sessions can be ended server-side.** Every JWT carries the account's `SessionVersion`, and the token-validated hook in `ServiceCollectionExtensions` refuses one that doesn't match the row. Changing or resetting a password and signing out all raise it, so sign-out ends every session of that account, not just the browser's. Change-password re-issues the caller's cookie. An integration test that changes the seeded admin's password has to mint a fresh client afterwards (`CreateAuthenticatedClient` reads the current version).
- **The first-run bootstrap lives only in `AdminBootstrap`** (called from `InitializeDatabase`) and creates an Owner. Login does not create accounts; an unknown email is just a failed login.
- **Lockout protection** is a set of `UserService` business rules (`BusinessRuleException`), not authorization checks: the instance must always keep one active Owner, and you can neither deactivate your own account nor change your own role (both would revoke the access you are using). The self rules are checked first, so that is the message you get when both apply.
- Frontend: `context/AuthContext.tsx` resolves `/admin/auth/me` once per admin-layout mount and is the only place the signed-in identity lives; role gating goes through `useCan(capability)` with the capability matrix in `constants/roles.ts` (mirrors the backend). Never inline a `role === "Owner"` check.

**Customer bookings** — no auth. Customers identify via `BookingRef` (short random string) or the encrypted recent-bookings cookie.

**Admin API keys** — the headless credential for `openresto-cli` and integrations (issue #319). `AdminApiKey` rows hold a SHA-256 of the raw `orst_<id>_<secret>` key (deliberately a fast hash, not `IPasswordService` PBKDF2 — the secret is 256 bits of CSPRNG output verified on every request; `ApiKeyCrypto` documents this). Presented via `X-API-Key`, never `Authorization`; the `AdminAuth` policy scheme forwards to the `ApiKey` handler when the header is present, else JWT, so policy-gated controllers accept either. Role and active status resolve live from the `AdminCredential` row at auth time — nothing is baked into the key. Keys are self-scoped PAT-style: an Owner mints/lists/revokes only their own, revoke is soft (`RevokedAt`) so audit entries keep resolving.

Six invariants:

- **Every `RequireAdmin`/`RequireOwner` action carries exactly one of `[RequiresScope]`, `[NoApiKeyAccess]`, or `[AllowAnyApiKey]`** — `ApiKeyScopeCoverageTests` reflects over all of them and fails otherwise, same structural floor as the audit coverage test. Scope resources (`ApiKeyScopes`) mirror the `AuditActions` noun groups; `audit`, `guests` and `email` are read-only; a `write` grant satisfies a `read` requirement, never the reverse.
- **The excluded surface stays excluded**: auth self-service, the SMTP credential surface (`EmailSettingsController`), notifications/push, and key management itself are `[NoApiKeyAccess]`. The one any-key endpoint is `GET api/admin/api-keys/self` (backs `openresto auth whoami`).
- **`email` is the read-only half of a `[NoApiKeyAccess]` controller, split out rather than carved into it** (#407): `EmailStatusController` shares the `api/admin/email-settings` route prefix and holds `status` + `failures` under `email:read`, because a marker on the controller and a different one on an action inside it is exactly the two-markers-on-one-action case `ApiKeyScopeCoverageTests` fails. There is deliberately no `email:write` — a key able to rewrite host, username and password would redirect every outgoing mail to a relay it controls. The failure list runs its recipient through `BookingGuestVisibility` for the same reason bookings do.
- **`guests` is a DTO redaction, not a gate**: a key with `bookings:read` but no `guests:read` gets bookings with customer name/email nulled, through `BookingGuestVisibility` only — never re-derive the condition at a call site.
- **The global rate limiter partitions keyed requests per client IP** (`apikey-ip:<ip>`, higher ceiling), never per header value — the limiter runs pre-auth, so a per-value partition would let rotated garbage headers mint unlimited buckets.
- **Audit rows name the acting key** (`AuditLogMiddleware` appends the key name to the actor display name), which is why `Name` is required at mint.

### Platform: one instance, many restaurants

The instance is run by the **platform** (the Owner admins) for restaurants that are not its staff. Six things hold it together, and the first two are what keep one restaurateur out of another's data:

- **A restaurateur is not an admin.** `UserRoles.Restaurateur` is outside `Assignable` and outside `RequireAdmin`/`RequireOwner`, so none of the admin endpoints answer to it (pinned over a list of them in `PlatformControllerTests`). It only exists through an invitation. `AuthPolicies.RequirePlatform` (Owners, today the same people as `RequireOwner`, kept as its own name) gates `/api/platform`; `RequireRestaurateur` gates `/api/onboarding`. Both are in `AuditRequestClassifier`, so every mutating call to them is audited, and both controllers are `[NoApiKeyAccess]`: a key that could mint an account link or read guests would be a privilege primitive.
- **One gate for a restaurateur's restaurants.** `OnboardingService.RequireRestaurantAsync` resolves the restaurant through a `RestaurantMember` row for the caller. Not a member, no such restaurant and an archived one are the same `404 platform.not_found`; a suspended one can be read but takes no write (`409 onboarding.suspended`). Ids inside a payload (a section, a table, a menu category) are checked against the restaurant's own, so an id from another restaurant is refused as an unknown one. Add new restaurateur endpoints through this gate and add them to `AnotherRestaurantsId_IsANotFound_ForEveryOperation`.
- **`Restaurant.Status` is the public switch** (`Published` by default, so every row that predates it stays live; `Draft`; `Suspended`). `Restaurant.IsListedPublicly` (not archived and published) is what every guest path asks: `RestaurantRepository` (`GetByIdAsync`, `GetAllActive*`) filters on it, so availability, holds, booking, waitlist and the public listing refuse a draft or suspended restaurant with the existing not-found; `SiteRepository` and `MenuService`'s public view do the same. Admin write paths use `FindByIdAsync` and still reach every restaurant (the admin overview counts only live ones). Bookings already taken survive a suspension and stay cancellable by their guests. Reactivation returns a restaurant that was live to `Published` and one that never was to `Draft` (`PublishedAt` decides, so unpublishing clears it).
- **Invitations are credentials.** `RestaurantInvitation` stores only the SHA-256 of a 256-bit token (`InvitationToken`); the link is returned once by `PlatformService` and mailed (`InvitationMail`, `fr`/`nl`/`en`, fixed month tables). An unknown, used, expired, revoked or foreign-address token is one `404 platform.invitation_invalid`. Accepting creates the `Restaurateur` account, its membership and the consent journal, and signs in. Accepting an invitation to a restaurant the account already runs sets a new password instead (the recovery path: the platform re-sends). A restaurateur password is at least 10 characters (the admin's 6 is too few for an account on the internet).
- **Consent is journalled with the text, not just the fact.** `LegalCatalog` (four French templates, `NeedsLegalReview` true until a lawyer validates them; every screen says so) carries a `Version` and a `ContentSha256` per document; sign-up refuses a missing document or an outdated version, and `LegalAcceptance` rows keep key, version, hash, e-mail and time, with **no foreign keys** so the proof outlives the account and the restaurant. Changing any wording means bumping `LegalCatalog.Version`.
- **The platform never reads guests by default.** The restaurants list is counts and dates (`TheListRowAndTheInvitationCarryNoGuestField` fixes its shape). The one door is `PlatformService.AccessGuestDataAsync`: a POST (so it is audited), refused without a 10–300 character reason before anything is read, and it records the reason on the audit entry. That door is the only one that asks for a reason. The admin booking screens still show guests to every Owner and Manager, with no reason asked and no limit to one location: that is the next thing to scope per restaurant, not something this layer solved. What they do now is **leave a trace**: every admin GET that returns guest identity is declared `[ReadsGuestData("<screen>")]` and lands a `guests.read` row (who, which screen, which location; never what was read), once per `AuditLogMiddleware.GuestDataReadWindow` (ten minutes) per person, credential (an API key's name rides on the actor), screen and location, so a polling dashboard is one row. `AuditCoverageTests` lists the nine declared reads and fails on a typed action returning a guest DTO that is not declared; a read answering a bare `IActionResult` can only be caught by that list, so **a new admin read of guests belongs on it**, and `ControllerBase.NoteGuestDataLocation` names the location for a read by record id. The legal texts say exactly this (`LegalTexts`: reads are logged, the platform door needs a reason, admin accounts are not limited to a location, a restaurateur's account is) and must not claim more until the scoping lands.
- **Guest data has a lifetime, and none is erased until a period is fixed.** `Restaurant.BookingRetentionMonths` is an `int?` (1–60): **`null` is no automatic erasure**, which is what every restaurant that predates the setting holds. The migration adds the column nullable with no default on purpose: backfilling 12 would have had the worker erase the names of everything older than a year about ten minutes after an upgraded instance first started, with no notice and no setting to stop it. A new restaurant starts at `BookingRetention.DefaultMonths` (12), set explicitly at each creation site (`PlatformService.CreateRestaurantAsync`, `RestaurantManagementService.CreateAsync`, `AdminService.CreateRestaurantAsync`, `DbSeeder`) and by the entity initializer, which EF overwrites with `null` when it reads a NULL row. The period is measured from when the sitting ended (`BookingRetention.IsExpired`; the repository's SQL predicate and the domain rule are pinned against each other at the boundary). Who fixes it: the platform, with `PUT /api/platform/restaurants/{id}/retention` (`{"months": n}` or `{"months": null}`; `RequirePlatform`, audited as `platform.retention_set` with the old and new value, `platform.retention_invalid` 400 outside 1–60, the usual `platform.not_found` for an unknown or archived restaurant; `RetentionModal` on the platform row, which checks the range in the button and again in the handler), or the restaurateur by saving step 1 of the assistant, which shows 12 for a restaurant with none and fixes it on save. `BookingRetentionWorker` runs `BookingRetentionService` daily: bookings lose name, e-mail and notes and get `AnonymizedAt` (the row stays for its counts), their reminder devices and failed-mail records are deleted, the `AdminNotifications` of those bookings (found by `BookingId`) lose `CustomerName` (set to empty; the notifications screen draws nothing for an empty name, as it does for "nearly full"), closed waitlist tickets lose their guest. The notification step runs before the bookings update because it finds its rows through the marker that update removes. A `null` or out-of-bounds period is skipped, never read as zero or as 12. With no stored default a `0` assigned in C# is stored as 0, so a test that needs an invalid period just assigns it.
- **The setup assistant composes the admin's services** (`RestaurantManagementService` for rooms and tables, `MenuService`, `SiteService`) behind that gate. Layout and menu saves are diffs by id; removing a table that has an upcoming booking is refused whole before anything changes (`onboarding.layout_in_use`), never done by nulling the booking's table. The legal identity (legal name, Belgian enterprise number checked by its control digits in `BelgianBusinessNumber`, optional VAT) is collected once and written to the restaurant and to the site's legal notice, which is what lets "Publier" take the site live. Publishing needs the three required steps (`OnboardingProgress.Required`: info, hours, layout) and switches on the site and the menu before it flips the status, so a refusal leaves a draft. The per-restaurant colour lives on `RestaurantSite.PrimaryColor` and paints the website only: the booking and menu pages still wear the instance's brand colour.
- **The platform space is `/admin/platform`, behind `manage:platform` (Owner only, mirroring `RequirePlatform`).** `components/admin/platform/PlatformScreen` lists restaurants with counts and dates only. Every modal's handler refuses on its own what the button is greyed for (a reason under 10 characters never reaches `accessPlatformGuestData`), because a disabled button is not a gate. `GuestDataModal` is the one place a restaurant's guests can be read: it states what the access is before asking, counts the trimmed reason as the server does, drops the data and the reason from the tree on any close (button or backdrop), writes nothing to storage, and says how many bookings it shows out of how many exist when the server cut the list. An invitation link is shown once (`InvitationLinkPanel`, same "Copied only once the write resolved" rule as the API-key secret): the server keeps a hash, so there is nothing to show again, and a re-send is the way back.
- **Legal pages are public routes (`/legal`, `/legal/[key]`) rendered from `/api/legal`, never from locale files.** The documents are French templates; every screen carries `LegalReviewBanner` while `needsLegalReview` is true, and the guest footer links them in every locale. Wording lives in `LegalTexts` on the backend, so a change there bumps `LegalCatalog.Version`.
- **The restaurateur's space is `/onboarding/*`, a surface of its own.** `app/onboarding/_layout.tsx` mounts `OnboardingSessionProvider` (not `AuthContext`: `/admin/auth/me` is closed to a restaurateur, so identity is read from `/onboarding/me`), opts out of the browser's language like the admin, sends `noindex` (an invitation link is a credential) and redirects to the home screen off web. Only the sign-in and `/onboarding/invitation/[token]` are reachable without a session. A 401 from any step goes to `useOnboardingCall`'s `onExpired` and is not worded by the step.
- **The wizard works on the whole state.** Every onboarding write answers with `OnboardingState`, which replaces the one `OnboardingWizard` holds, so the stepper and `PublishPanel` are never a reload behind and no step re-derives completeness. The opening stage is `?step=`, else the first step still to do, else the preview (`utils/onboardingStages.ts`). Rooms and tables are edited as drafts keyed by `draft-N` strings and sent as a diff by id (`utils/onboardingLayout.ts`); prices are typed in the active language's separator and converted to cents by `parseDishPrice`, an empty price being a dish with none shown, never zero. A refusal is shown beside the field that caused it, not in a toast. Switching stage discards a step's unsaved edits.

### The CLI and its OpenAPI contract

`openresto-cli/` is a standalone TypeScript package (Node 24, `commander` as the only runtime dep). It is not its own product — it's an extension of OpenResto — so its `package.json` version stays synced with the root/frontend version on every release (`scripts/check-release-version.sh` enforces this the same way it does for the other two packages) and it ships two ways from the same tag: the npm package `openresto-cli` (the `publish-npm` job in `release.yml`, gated on `verify-version` and on `npm test`) and the Docker image `ghcr.io/karanshukla/openresto-cli:<tag>` (built alongside backend/frontend/nginx). npm is the documented default; the image is for hosts with Docker but no Node 24. `openresto-cli/LICENSE` is a copy of the root one because npm only bundles a LICENSE from the package directory, and `files` excludes `dist/**/*.test.js` so the compiled node:test suite stays out of the tarball. **npm auth is trusted publishing (OIDC), not a token**: the job's `id-token: write` grant is the whole credential, there is no `NPM_TOKEN` secret, and provenance is attached automatically so `--provenance` must not be passed. npmjs.com pins the trusted publisher to the workflow _filename_, so renaming `release.yml` silently stops npm publishing until the package's trusted-publisher settings are updated to match. User docs live in `openresto-cli/README.md`. Two conventions are load-bearing:

- **No secret is ever accepted as argv** (`ps` exposure — the same rule `scripts/demo_data.py` follows for the admin password). `auth login` and `users reset-password` prompt with hidden input or read stdin, and neither has a flag that would carry the value; `OPENRESTO_URL`/`OPENRESTO_API_KEY` env vars override the `~/.config/openresto/config.json` profile (written mode 0600).
- **The committed contract must match the controllers byte-for-byte.** `tools/OpenApiExport` boots the real API in-process (`WebApplicationFactory`, in-memory SQLite — build-time MSBuild generation was tried and rejected; the tool's doc comment says why) and writes `openresto-cli/openapi/v1.json`; `openapi-typescript` compiles it to `openresto-cli/src/generated/api.d.ts`. The `openapi-drift` CI job regenerates both and fails on any diff, so an API-shape change must ship with:

  ```bash
  dotnet build
  cd tools/OpenApiExport && dotnet run --no-build -- ../../openresto-cli/openapi/v1.json
  cd ../../openresto-cli && npm run generate:types
  ```

  Both files are listed in `.prettierignore` on purpose: the drift check compares against what the generators emit, so no formatter may touch them. Commands are hand-written over the generated types — don't let generated operation names dictate CLI structure.

### Production kit (`deploy/`)

`deploy/` is the single-VM install the hosting guide `docs/HEBERGEMENT.md` describes: `docker-compose.prod.yml` (Caddy for HTTPS, then the release `nginx`, `backend`, `frontend` images), `backup/` (backup, restore, shared helpers), `systemd/` timer, `update.sh`, `smoke.sh`. `deploy/tests/stack.test.sh` boots the stack and exercises backup and restore; the `deploy-kit` workflow runs it. Three things are easy to break:

- **Caddy sits in front of the release nginx, so nginx must trust it for the client address.** The backend reads one `X-Forwarded-For` hop and nginx appends the address it saw; without `deploy/nginx-realip.conf` that hop is Caddy's, every guest shares one rate-limit bucket and hold quota, and the audit trail records Caddy's IP. The stack test fails if nginx's client address is Caddy's.
- **The backup is SQLite's own online `.backup`, never a copy of the live file.** It also carries `dp-keys/` and the media, and the restore refuses an archive whose checksum or `integrity_check` fails before it touches anything. The snapshot of a WAL database opens as WAL, so it cannot be opened on a read-only mount.
- **Only Caddy publishes ports.** Docker bypasses the host firewall for published ports, so a `ports:` on any other service is open to the internet whatever `ufw` says.

### Codespaces demo (`.devcontainer/`)

`.devcontainer/demo.sh` runs the repository's `docker-compose.yml` stack with the demo dataset, for a GitHub Codespace or a laptop with Docker (`docs/HEBERGEMENT.md` section 13). The Codespace reads its recipe from the branch it is opened on, so a branch only gets the demo if it carries `.devcontainer/`. Two things are easy to break:

- **The committed development credentials must not reach a demo.** `docker-compose.yml`'s env file carries a committed JWT key and admin password; a Codespace port made public would accept a forged admin session. `docker-compose.demo.yml` replaces both with values `demo.sh` generates into the git-ignored `.devcontainer/demo.env`, which `.dockerignore` keeps out of build layers.
- **The dataset sets the site address to `https://openres.to`, and the QR codes encode the brand's website URL.** `demo.sh` rewrites it to the demo's own origin on every start; without that a phone scanning a code opens the public demo instead.

docs.openres.to is a Starlight (Astro) site whose pages are Markdown in `docs-site/src/content/docs/` — `self-hosting/`, `guides/` and `api/`. It is static and deploys as a Cloudflare Workers static-assets site (`docs-site/wrangler.jsonc`), so nothing on the VPS serves it. ### Admin audit trail

`AdminAuditEntry` is an append-only record of who did what, surfaced at `/admin/activity`. Six things about it are easy to get wrong:

- **Coverage is structural, not a list.** `AuditLogMiddleware` writes a row for every mutating request to an endpoint gated by `RequireAdmin`/`RequireOwner` (`AuditRequestClassifier`), so an endpoint added tomorrow is audited the day it ships. `IAuditScope` only adds the readable part on top — a domain action key from `AuditActions`, a target, a summary, a diff. An unenriched request still lands a row keyed `http.post`. The corollary is that a gate which names no policy (a bare `[Authorize]`, or one listing raw roles) is invisible to the floor; `AuditCoverageTests` reflects over every controller action and fails on one. Reads are outside the floor except one kind: a GET declared `[ReadsGuestData]` lands a `guests.read` row (see the platform section).
- **The middleware is outermost in `Program.cs`, above `UseExceptionHandler`.** It records after the pipeline unwinds, so `Response.StatusCode` is the 400 the caller actually received rather than the 200 it still was inside MVC's filters, and `RemoteIpAddress` is the client's as rewritten by `UseForwardedHeaders`. Moving it inwards silently changes both.
- **The write uses its own DI scope.** Sharing the request's `DbContext` would make the audit `SaveChanges` flush whatever a half-finished service left tracked on it — committing, as a side effect of logging, the mutation that threw.
- **Entries never carry secrets or customer PII.** `ChangesJson` is only ever written by a service naming a field through `RecordChange`, so the recorded set is an allow-list by construction; `AuditFields.IsProtected` masks the value on top of that, for credentials and for customer identity alike. Booking history is deliberately GDPR-purgeable, so entries reference bookings by ref and id only — never a customer name, email or phone, in `TargetLabel` or `Summary` either. `Path` is stored without its query string for the same reason (admin list screens filter by customer email).
- **There is no write and no delete endpoint.** An admin who can erase the audit log has no audit log. Rows leave only through `AuditRetentionService` (default 365 days, `Audit:RetentionDays`, driven daily by `AuditRetentionWorker`). The demo reset wipes the table for a sharper reason: the demo's admin password is public, so its entries are visitors' actions and visitors' IPs shown to every other visitor.
- **Services take `IAuditScope? audit = null`** as an optional last constructor parameter, falling back to `NullAuditScope.Instance`. That is what keeps the ~30 test classes that construct services by hand compiling with no arrangement.

### Deletion & cascade behaviour

**Table / Section deletion** — `Booking.TableId` and `Booking.SectionId` are **nullable** (`int?`). Deleting a table or section does **not** cascade-delete its bookings; instead, `DeleteTableAsync` and `DeleteSectionAsync` in `RestaurantManagementService` explicitly null those FK columns on affected bookings before removing the parent row. The DB FK is `ON DELETE SET NULL`. `ToDetailDto` in `AdminService` returns `"Table"` / `"Section"` as display fallbacks when the FK is null.

**Restaurant deletion is archive-then-purge, enforced server-side.** `DELETE /admin/restaurants/{id}` cascades to every section, table and booking, so `AdminService.DeleteRestaurantAsync` throws a `BusinessRuleException` unless the restaurant is already `IsArchived` — the two-step is a rule, not a UI convention, and the archive step _is_ the undo. The endpoint and its `GET /admin/restaurants/{id}/delete-preview` preflight (section/table/group/booking counts for the confirmation) are both `RequireOwner`, matching user management; the frontend mirrors that with the `delete:location` capability.

`/admin/locations` has **one location selector**, listing archived locations alongside active ones. Two selectors on that screen (a page picker plus a Danger Zone picker) is what let an admin edit one location and destroy another, and is why `DangerZone` is gone. Archive lives at the foot of the selected location's card behind a confirm sheet; selecting an archived location swaps the editable card for `ArchivedLocationPanel` (read-only, one-press Restore, and — Owner only — the delete flow). Restore has no confirmation on purpose: reversible actions do not get gates. `RestaurantDto` never carries archived rows, so the archived panel renders from the admin lookup list, and both archive and restore refetch `fetchRestaurants()` afterwards.

Booking history is intentionally **GDPR-purgeable** via the existing `PurgeBookingAsync`, so "losing history on restaurant deletion" is not a concern by design.

### Testing

- **Backend**: xUnit + Moq. Tests live in `OpenRestoApi.Tests/`. Services are tested in isolation with mocked repos and a mock `ISystemClock` (inject `MockSystemClock` to control time-dependent hold/availability logic).
- **Backend coverage numbers**: the reported figure (CI badge, Coveralls, PR comment) excludes EF migrations, matching a local `dotnet test /p:CollectCoverage=true` run — both read the same exclusion list, just from different places. `OpenRestoApi.Tests.csproj`'s `<Exclude>` governs the MSBuild integration (`coverlet.msbuild`, used for local runs); CI's `--collect:"XPlat Code Coverage"` reads exclusions from `OpenRestoApi.Tests/coverlet.runsettings` (passed via `--settings`) instead, since the VSTest collector doesn't read the csproj property. The runsettings file sits beside the csproj it mirrors so the two `<Exclude>` values are edited together — see `coverlet.runsettings` for why they must stay in sync.
- **Frontend**: Jest + React Native Testing Library. 100% coverage target. E2E with Playwright (`tests/e2e/`).
- **The suite runs on two platforms, and `npm test` is only one of them.** `jest-expo`'s default preset sets `haste.defaultPlatform: "ios"`, so a plain `npm test` resolves `.ios.*`/`.native.*` and reports `Platform.OS === "ios"` — which means it silently never executes the Android branch of a `Platform.OS` check, nor an `.android.*` module. `jest.config.android.js` is the other half (`npm run test:android`); it inherits everything from `package.json`'s jest block so the two cannot drift, and CI runs them as two parallel jobs, `Frontend CI` and `Frontend Tests (Android)`. Coverage comes off the iOS run only, so the numbers stay comparable across the two. Two things follow for test authors: a value that differs per OS belongs in the test of the component that decides it (`KeyboardAvoider` pins `behavior` on both branches; the screens that mount it assert only that the shell is there), and an assertion that is exactly right on one platform is a failure waiting on the other. The transform in that config is rebuilt from the base preset rather than inherited, because `jest-expo/android/jest-preset` sets only `caller.platform` and drops the babel preset the default one injects — a repo with no `babel.config.js`, like this one, otherwise dies parsing React Native's flow-typed sources.
- **Testing async effects with delays**: for `useEffect` code that fires inside a `setTimeout`, use `waitFor` with a custom `timeout` (e.g. `{ timeout: 1000 }`) rather than fake timers — the real timer fires within the `waitFor` polling window. Example: `await waitFor(() => expect(mockFn).toHaveBeenCalled(), { timeout: 1000 })`.
- **Testing cross-platform scroll**: In the jsdom + RN test renderer environment, `View` refs are RN component instances (NOT DOM elements), so `HTMLElement.prototype.scrollIntoView` is never reachable. Test the web scroll path by waiting past the timeout delay and asserting no crash (the `scrollIntoView?.()` optional chain is a no-op but the line is still covered). For the native path, hand the component a stub scroller whose `getInnerViewRef()` returns a sentinel and whose child's `measureLayout` invokes its success callback with the geometry the case needs — see `tests/components/common/KeyboardAwareScroll.test.tsx`. Nothing lays out in jsdom, so real measurement never arrives.
- **CI ZAP scan**: runs against the full Docker stack; the OpenAPI spec (`/openapi/v1.json`) is used as the scan target so ZAP discovers all endpoints. Ignored rules are listed in `.github/.zap-rules.tsv`.
- **Date-boundary check** (`.github/workflows/date-boundary.yml`): weekly (and on demand), runs Jest and the full Playwright suite with the runner's clock pinned to the last day of the current month. A test that computes "tomorrow" and expects it on screen passes every day but the 31st, which is how three of them reached `main` at once on 2026-08-31 — the date picker renders one calendar month, so on a month end there is no tomorrow in its grid. Pin the **runner's** clock, never Playwright's `page.clock`: the containers share the host kernel clock and Chromium runs on the host, so `date -s` moves the backend, the frontend and the browser together, where `page.clock` would move only the browser and leave it disagreeing with the server computing availability. The pinned date is computed, not listed, so it rotates through 28-, 29-, 30- and 31-day months over a year. Builds and installs run before the clock moves, since a skewed clock breaks TLS; the clock is restored unconditionally afterwards, and a failure to move it fails the job rather than silently running on today's date.
- **Migration safety check** (`.github/workflows/migration-check.yml`): triggers on any PR/push that adds or modifies files in `OpenRestoApi.Infrastructure/Migrations/` or `AppDbContext.cs`. Detects which migration files are new, generates baseline SQL (0 → last old migration), generates upgrade-only SQL (last old migration → HEAD), applies both paths to separate SQLite databases, and asserts their schemas match. Also generates an idempotent script as a sanity check. Does not trigger if no migration files changed.
- **Backup/restore**: see `docs-site/src/content/docs/self-hosting/backup-restore.md` for procedures covering named volumes, bind mounts, WAL checkpointing, automated cron backups, online `.backup` snapshots, and the safe upgrade path.
